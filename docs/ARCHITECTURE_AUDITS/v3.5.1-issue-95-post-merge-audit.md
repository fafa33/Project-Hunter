### 5. Canonical persistence and strict-known reads

Requirement: Immutable insert-or-identical; divergent duplicate rejection;
append-only successor lineage; **strict-known filtering by effective,
recorded, and known cutoffs**; superseded/invalidated exclusion; deterministic
exact-ID and logical-history reads; exact source/evidence version
preservation; unresolved-conflict queries; no standalone valuation database.

Evidence (verified):
- Canonical DB only: `repository.py:19` (`DEFAULT_VALUE_CAPTURE_DB =
  Path("data/data_ops.sqlite")`), confirmed by
  `test_canonical_default_and_generic_sql_persistence` asserting the legacy
  domain tables (`fundamental_evidence_records`, `supply_basis_snapshots`,
  `value_capture_rule_snapshots`) do not exist as real SQL tables — records
  are opaque snapshot payloads in the shared `persistence_records` table.
- Insert-or-identical / divergent rejection: generic layer
  `src/hunter/persistence/sql/repositories/base.py:27-51` (`SQLRecordRepository.save`)
  — same ID + same canonical hash returns existing record; same ID +
  different hash raises `PersistenceIdentityConflictError`, mapped to
  `ValueCaptureIntegrityError` in `service.py:76-78`.
- Append-only lineage / branching rejection: `service.py:105-126`
  (`insert_record`), tested by
  `test_branching_corrections_are_rejected_and_replay_is_strict_known` and
  `test_concurrent_corrections_cannot_branch_lineage` (real `ThreadPoolExecutor`
  race, using SQLite `BEGIN IMMEDIATE` for serialization).
- Unresolved-conflict queries: present and tested symmetrically for **all
  three** families (`unresolved_evidence_conflicts`,
  `unresolved_supply_conflicts`, `unresolved_rule_conflicts` —
  `repository.py:100-129`).
- Logical-history reads: present and tested symmetrically for all three
  families (`evidence_history`, `supply_history`, `rule_history`).

**Gap found:** strict-known, point-in-time selection
(`_strict_known` / `strict_known_supply` / `strict_known_rule`,
`repository.py:131-191`) is implemented and tested **only for
`SupplyBasisSnapshot` and `ValueCaptureRuleSnapshot`**. There is **no
`strict_known_evidence` method** on either
`SupplyAndValueCaptureRepository` or `SupplyAndValueCaptureService` for
`FundamentalEvidenceRecord`. Confirmed by direct grep of
`src/hunter/value_capture/{repository,service}.py` — only
`strict_known_supply` and `strict_known_rule` exist. `evidence_history()`
returns the complete unfiltered append-only history, not a
cutoff-selected point-in-time answer. PR #102 itself explicitly recorded
this exact gap under "Remaining Issue #95 gaps: ... strict-known evidence
replay," and no subsequent merged PR (#104, or any other) closed it.

Issue #95 requires "strict-known filtering by effective, recorded, and
known cutoffs" as a persistence semantic applying to the whole domain, and
ADR 0021 requires every transitive record — including
`FundamentalEvidenceRecord`, the base of the evidence chain that
`SupplyBasisSnapshot` and `ValueCaptureRuleSnapshot` both depend on — to be
selectable under strict-known replay. Without a strict-known evidence read,
a future consumer has no way to deterministically select "the evidence
known as of cutoff X" without re-implementing the cutoff logic outside the
service boundary, which would violate the service-ownership requirement in
section 4 above.

Status: **PARTIALLY VERIFIED**

# Architectural Findings

1. **Missing strict-known read for `FundamentalEvidenceRecord`** (see
   Requirement 5). This is the most significant substantive gap: the base
   evidence layer that both `SupplyBasisSnapshot` and
   `ValueCaptureRuleSnapshot` depend on cannot itself be queried under
   strict-known, point-in-time selection through the service. Any future
   consumer needing "the evidence known as of cutoff X" must currently
   filter `evidence_history()` results outside the service boundary,
   which both duplicates logic that already exists twice (once for supply,
   once for rule) and creates a channel for a future caller to get the
   cutoff logic wrong without the service catching it.

2. **PR #100 ("Committee authority runtime") is a mislabeled no-op merge.**
   Verified directly against git history, not the PR description: `git diff
   0235528 7aac6d8` (PR #99's merge result vs. PR #100's merge result) is
   **empty** — PR #100 introduced zero net changes to `main`. Its title and
   body describe "approved authoritative committee runtime wiring,"
   "dashboard path" tests, and "backtesting_reliability" gating — none of
   which appear anywhere in its actual diff, which is byte-identical to PR
   #99's value-capture supply-basis changes. This is a concrete illustration
   of exactly the risk this audit was chartered to guard against (never
   trust PR descriptions): the PR record for #100 is disconnected from what
   actually merged. It caused no functional harm (net diff is zero) but it
   corrupts the audit trail — anyone reading PR #100's description without
   independently diffing it would believe committee-runtime work happened
   here when none did.

3. **Stale/missing implementation documentation.**
   `docs/IMPLEMENTATION_REPORTS/v3.5.0-supply-basis-value-capture.md` still
   describes the standalone `data/value_capture/runtime/value_capture.sqlite`
   database, `supply-value-capture-v3.5.0-001` migration ID, and per-domain
   SQL tables — all of which PR #97 replaced with the canonical
   `data/data_ops.sqlite` snapshot-based persistence. This document was never
   updated or superseded. No `docs/IMPLEMENTATION_REPORTS/v3.5.1-*.md` exists
   at all, despite `docs/SPRINTS/v3.5.1.md`'s own "Definition of Done"
   explicitly requiring "An implementation report records the exact final
   commit and verification" and "Implementation and architecture
   documentation match it." Neither condition is currently satisfied on
   `main`.

4. **Onchain provider source is enabled by default with a live public
   endpoint.** `configs/value_capture_sources.yaml`'s
   `verified-onchain-value-capture` source has `enabled: true` against
   `https://ethereum.publicnode.com`. This is within the provider-eligibility
   rules of ADR 0021 (onchain observation is a legitimate evidence type) and
   is not a defect, but it is the only enabled source in the registry and
   its real-world reachability/behavior was not and could not be exercised
   by this audit. Worth confirming this is an intentional production
   registration rather than a leftover from development.

5. **No semantic check that a rule's referenced evidence type is compatible
   with its claimed cash-flow mechanism.** `_require_evidence` in
   `service.py` verifies identity, provenance, quality, and chronology of
   referenced evidence, but does not check that (for example) a
   `fee_distribution` rule references evidence whose `evidence_type` is
   capable of establishing an actual fee flow, as opposed to, say, a
   `governance_record` that merely mentions fees. Given this issue is
   explicitly evidence-foundation-only and full pathway semantics are
   reserved for the future valuation methodology, this is a reasonable
   scope boundary rather than a violation — noted for completeness, not
   scored as a failure.

# Regression Assessment

- **No regression in Market Validation scoring, ranking, Dashboard, or
  Opportunity pipelines.** Verified no code path outside
  `src/hunter/value_capture/` was touched by PRs #97–#99, #101, #102, #104
  (PR #96 was docs-only; PR #100 was a no-op — see Finding 2). `ruff`,
  `black`, `mypy`, and the full `pytest` suite (1107 tests) all pass on
  current `main` HEAD.
- **Pre-existing, unrelated circular-import fragility identified during
  audit — not a regression introduced by PRs #96–#104.** A cold,
  first-touch import of `hunter.committee` in a fresh process (before any
  other `hunter.*` submodule has populated `sys.modules`) raises
  `ImportError: cannot import name 'InvestmentCommitteeAssessment' ...
  (most likely due to a circular import)`, caused by a cycle:
  `hunter.committee.__init__` → `...engine` → `...metrics` → `...models` →
  `hunter.opportunity.models` → `hunter.opportunity.__init__` →
  `...persistence_service` → `hunter.persistence.experimental` →
  `hunter.committee.models`. Verified this cycle already exists at commit
  `eb43e3a` (immediately after PR #96, before any value-capture code
  changed) via `git worktree`, and that `src/hunter/persistence/experimental.py`
  and `src/hunter/committee/models.py` are byte-identical between that
  commit and current HEAD. It does not affect the documented verification
  command (`pytest` run from repo root touches these modules in a safe
  order first) or the installed `hunter` CLI (confirmed by running `hunter
  committee-authority` directly), only a from-scratch import of
  `hunter.committee` as the very first `hunter.*` import in a process. Not
  in scope for Issue #95, but worth a follow-up ticket since it is a latent
  hazard for any new entry point that imports `hunter.committee` first.
- **Value-capture registry enabling a live onchain provider by default**
  (Finding 4) is a soft regression-risk surface for future acquisition runs
  that actually invoke it, though no code in this remediation activates
  scheduled acquisition against it.

# Final Verdict

**CHANGES REQUIRED**

Rationale: the implementation is well-engineered, honors ADR 0021's
authority boundaries, keeps all four valuation-family inputs genuinely
unavailable, introduces no regression in any adjacent runtime, and passes
every required quality gate (ruff, black, mypy, and the full 1107-test
pytest suite) on the exact `main` HEAD. However, Issue #95's own completion
criterion is "Hunter can durably validate, version, correct, persist,
query, and **strict-known replay** attributable fundamental evidence[...]"
— and strict-known replay for `FundamentalEvidenceRecord` specifically does
not exist, while the equivalent capability does exist and is tested for the
other two record families. This is a concrete, verifiable, non-cosmetic gap
against an explicit acceptance criterion, not a matter of interpretation.
Independently, PR #100 is a mislabeled no-op merge that corrupts the audit
trail, and the sprint's own Definition of Done ("implementation report
records the exact final commit and verification," "documentation match[es]"
the implementation) is unmet — the only implementation report on file
describes an architecture (`data/value_capture/runtime/value_capture.sqlite`)
that PR #97 deliberately removed.
