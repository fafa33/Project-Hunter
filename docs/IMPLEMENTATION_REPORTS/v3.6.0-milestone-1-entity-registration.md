## Why this milestone is scoped the way it is

ADR 0022's own Scope section is explicit: *"No specific project is named as satisfying these criteria today. Registering a concrete entity that satisfies all four criteria... is implementation work, not an architectural decision, and is out of scope for this ADR."* Milestone 1's job is exactly that implementation work — nothing more. `hunter.market_facts` and `hunter.value_capture` (Issues #88/#95, both closed and independently audited) already provide every model, repository, and service required; ADR 0022 does not authorize a new schema, and none was added. The only new code in this milestone is a thin CLI orchestration entry point that wires an operator-supplied manifest to those already-audited services — no new authority rule, validation, or business logic was introduced anywhere in this change.

## Entity Selection Criteria (objective, config-only-swappable)

The user-facing requirement for this milestone was explicit: the implementation must be **fully entity-agnostic**, and any future entity must be able to replace the pilot **via configuration alone**, with no change to models, repositories, services, schema, or CLI code. This section defines the objective checklist any candidate entity must satisfy, derived directly from ADR 0022 §"Scope: the first supported entity class," plus two practical/operational criteria this repository's evidence-acquisition surface already requires in practice. A future entity satisfying this checklist can be registered by adding config entries only — see "How to swap the pilot entity" below.

| # | Criterion | Source | What it constrains |
|---|---|---|---|
| 1 | Single-chain, non-wrapped, non-bridged native representation | ADR 0022 Scope condition 1 | The `representation_id` bound in `configs/market_fact_sources.yaml` and used as `EconomicClaimIdentity.representation_id` must denote one canonical chain-native representation, never a wrapped/bridged/aggregate one (ADR 0005). |
| 2 | Exactly one disclosed value-capture mechanism from the ADR-0022-permitted `ValueCaptureRuleType` allow-list (`fee_distribution`, `revenue_distribution`, `buyback_and_burn`, `staking_distribution`, `redemption_entitlement`, `collateral_entitlement`) | ADR 0022 Scope condition 2 | At least one **enabled** source in `configs/value_capture_sources.yaml` must declare a `rule:<permitted-type>` capability that can be attested for the entity. |
| 3 | Circulating, total, and fully diluted supply independently observable and internally coherent (`circulating <= total <= fully_diluted`) | ADR 0022 Scope condition 3 | The entity's supply facts must be acquirable through an existing `market_facts` or `value_capture` source with `supply:*` capabilities, and must pass `SupplyBasisSnapshot`'s existing coherence checks unmodified. |
| 4 | At least one accepted, non-conflicted `FundamentalEvidenceRecord` whose `attribution_rule_id` matches an accepted `ValueCaptureRuleSnapshot`, with an accounting period inside the valuation horizon | ADR 0022 Scope condition 4 | A real, citable official/on-chain disclosure must exist and be acquirable today — not merely plausible in the future. |
| 5 (practical) | The entity has a stable, unambiguous listing on an already-integrated market-fact provider (currently CoinGecko) | Operational — `hunter.market_facts` has exactly one implemented provider today | Without this, criterion 3's supply facts and independent price/market-cap corroboration cannot be acquired through existing code. |
| 6 (practical) | The value-capture mechanism is described in a citable, publicly reachable official document or reproducible on-chain observation, independent of this repository | Operational — `FundamentalEvidenceRecord.source_reference` must be auditable by a third party | Prevents a pilot selection that cannot be independently re-verified by a future auditor. |

None of these six criteria mention any specific entity by name. Registering a different entity that satisfies all six requires editing only `configs/market_fact_sources.yaml` and `configs/value_capture_sources.yaml`, plus authoring a new acquisition manifest — no file under `src/hunter/` changes.

## Pilot Selection Rationale: Sky (SKY)

Sky (ticker `SKY`, the rebranded MakerDAO governance token) was selected as the **pilot** entity registered under Milestone 1, evaluated against the six criteria above:

1. **Single-chain, non-wrapped representation.** SKY is a native Ethereum ERC-20 token at `0x56072c95faa701256059aa122697b133aded9279` (confirmed via Etherscan). No wrapped or bridged representation is used.
2. **Disclosed value-capture mechanism.** Sky Protocol operates the **Smart Burn Engine**, an on-chain mechanism that allocates protocol surplus to buy back and permanently burn SKY tokens — a `buyback_and_burn` rule under ADR 0022's permitted allow-list, documented at the protocol's official developer documentation (`developers.sky.money/core-protocol/smart-burn-engine/`) and ratified through Sky governance (Maker Core governance forum). This is registered in `configs/value_capture_sources.yaml` as the `sky-protocol-tokenomics-disclosure` source with `rule:buyback_and_burn`.
3. **Supply coherence.** Circulating, total, and max supply are published on CoinGecko (provider listing id `sky`) through the already-integrated `coingecko-coin-market-facts` source, satisfying `SupplyBasisSnapshot`'s existing coherence checks without any new provider code.
4. **Citable fundamental evidence.** The Smart Burn Engine's parameters (daily allocation, activation) are documented in Sky's official developer docs and were ratified through an on-record governance proposal ("Introduction of Smart Burn Engine and Initial Parameters," Sky governance forum) — an independently reproducible, citable `official_disclosure` source.
5. **Provider coverage.** SKY has a stable, unambiguous CoinGecko listing (`coingecko.com/en/coins/sky`), usable today through the already-implemented `CoinGeckoObservedMarketFactProvider`.
6. **Independent auditability.** Both the burn mechanism and the supply facts are published by parties independent of this repository (Sky Protocol's own documentation and governance forum; CoinGecko as a third-party aggregator) and are re-verifiable by a future auditor without relying on this repository's own prior claims.

**One caveat is disclosed explicitly, not glossed over:** SKY's value-capture flow is **governance-directed**, not an immutable protocol guarantee — Sky governance controls whether, and at what rate, surplus is allocated to buybacks-and-burns, and that rate has changed by governance vote before. This is consistent with `ValueCaptureRuleSnapshot.governance_or_contract_authority`, which the record family already models explicitly for exactly this situation, and with ADR 0022's requirement that `FundamentalEvidenceRecord.accounting_period_end` stay inside the valuation horizon (a governance change outside that window does not retroactively invalidate an already-accepted evidence record; a future governance change is picked up by ordinary correction/supersession, not by this milestone).

GMX (perpetuals-DEX fee-distribution token) was considered as an alternative candidate during design and rejected: its fee-distribution flow is split across multiple chains with per-chain distribution parameters, which does not cleanly satisfy criterion 1's single-chain, non-aggregate representation requirement without additional identity-modeling work this milestone is not authorized to do.

## How to swap the pilot entity (proof of entity-agnosticism)

To register a different entity in place of, or in addition to, Sky:

1. Add an `identity_bindings` entry to the existing `coingecko-coin-market-facts` source (or a new market-fact source) in `configs/market_fact_sources.yaml`.
2. Add an enabled source with the required `rule:*`/`evidence:*`/`supply:*` capabilities to `configs/value_capture_sources.yaml`, or reuse an existing enabled source if its capabilities already cover the new entity.
3. Author a manifest JSON file (see `hunter valuation-evidence acquire --help` usage below) referencing the new entity's identity.
4. Run `hunter valuation-evidence acquire <manifest.json>`.

No file under `src/hunter/` requires modification for this. `src/hunter/valuation_evidence/command.py` contains zero references to "Sky," "SKY," Bitcoin, or any other entity name — it is verified by `tests/test_cli_valuation_evidence_acquire.py`, whose fixtures use an entirely synthetic entity (`entity:test-token`) unrelated to Sky, to prove the orchestration path itself carries no entity-specific logic.

## Files Changed

- `configs/market_fact_sources.yaml` — added one `identity_bindings` entry to the existing, unmodified `coingecko-coin-market-facts` source, binding Sky's canonical identity to CoinGecko listing id `sky`. The Bitcoin binding already present is untouched.
- `configs/value_capture_sources.yaml` — added one new, generic, **enabled** source (`sky-protocol-tokenomics-disclosure`) with `evidence:official_disclosure`, `supply:circulating_supply`/`supply:total_supply`/`supply:burned_supply`, and `rule:buyback_and_burn` capabilities. No `identity_bindings` field exists on this registry by design (value-capture identity is asserted per-acquisition through `EconomicClaimIdentity`, not bound at the registry level) — this source itself carries no entity reference and is reusable by any future entity whose official disclosures live at the same host, or can be copied as a template for a different host.
- `src/hunter/valuation_evidence/__init__.py` (new) — re-exports `main`.
- `src/hunter/valuation_evidence/command.py` (new) — the sole new business-logic-free CLI orchestrator. Reads a JSON manifest describing either a `market_fact` or a `value_capture` (`evidence`/`supply`/`rule`) acquisition operation, constructs the exact typed objects (`MarketFactRequest`/`MarketFactIdentity`, or `EconomicClaimIdentity` + `RegisteredValueCaptureProvider.acquisition(...)`) that `tests/test_value_capture_v3_5_0.py` and `tests/test_market_facts_v3_4_0.py` already exercise directly, and calls the existing, already-audited `ObservedMarketFactService.ingest` / `SupplyAndValueCaptureService.ingest_evidence|ingest_supply|ingest_rule`. It performs no validation, authorization, hashing, or persistence of its own — every one of those responsibilities remains exclusively owned by the pre-existing services. Value-capture provider signing-key material is read from two environment variables (`HUNTER_VALUE_CAPTURE_SIGNING_KEY_ID`, `HUNTER_VALUE_CAPTURE_SIGNING_KEY`), mirroring the existing `HUNTER_APPLICATION_ROOT` operational-secret pattern already used by `hunter.committee.command` — it is never accepted from the manifest file, since manifests are not a secrets channel.
- `src/hunter/__main__.py` — added one dispatch branch for `valuation-evidence`, mirroring the existing `committee-authority` dispatch exactly.
- `tests/test_cli_valuation_evidence_acquire.py` (new) — 6 tests: market-fact acquisition end-to-end (injected transport, no live network call), a full evidence → supply chain acquired through three sequential CLI invocations, a fail-closed signing-key-env-var test, an unsupported-provider rejection test, a `hunter.__main__` dispatch smoke test, and a config-file regression test asserting (a) the market-fact registry is bound to more than one entity and (b) at least one enabled value-capture source discloses a permitted rule — both assertions exist specifically to catch any future regression back toward a single-entity-hardcoded configuration.

No file under `src/hunter/market_facts/`, `src/hunter/value_capture/`, `src/hunter/committee/`, or `src/hunter/market_validation/` was modified. No model, repository, or service class was added, removed, or changed.

**Known limitation, disclosed rather than worked around: ADR 0022 Scope criterion 3 is not fully satisfied.** CoinGecko's live `max_supply` for Sky (`23462665147.3`) is observed to be fractionally *below* its own `total_supply` (`23462665147.36596`) for this snapshot — almost certainly a provider precision/staleness artifact (the two values differ by ~2.8×10⁻¹² relatively), not a real economic distinction, but `scripts/acquire_sky_supply_basis.py`'s `build_supply_payload` correctly refuses to fabricate, round, or otherwise force a `fully_diluted_supply` value that the provider did not itself report as coherent with `total_supply` — per this repository's standing anti-fabrication constraint and `SupplyBasisSnapshot`'s own unmodified `total<=fully_diluted` invariant. Circulating and total supply *are* independently observable and coherent (`circulating <= total`, confirmed). The fully-diluted leg of criterion 3 is therefore **not currently demonstrable for Sky without either a corrected/alternate provider figure or a policy decision on how to treat this precision gap** — flagged here for maintainer decision rather than concealed.

Independently re-verified directly against the tracked database via `SupplyAndValueCaptureRepository.strict_known_supply` as part of this update, alongside the pre-existing evidence/rule records (all `quality_state = accepted`). The database diff introduced by this acquisition and the evidence correction touched only `record_type = "snapshot"` rows — no `automation-job`/`automation-run` row changed, confirming no recurrence of the prior pollution incident. ## Risk Assessment

- **Signing-key operational risk**: `RegisteredValueCaptureProvider` requires a durable signing key per the v3.5.0 post-merge audit's remediation (persistent, not regenerated per-process). This milestone does not provision that key — it reads it from environment variables an operator must set before running the acquisition CLI in any real environment. Running the command without the env vars set fails closed with a clear `ValueError` (covered by `test_missing_signing_key_env_var_fails_closed`), not a silent no-op or a forged/unsigned write.
- **Governance-dependent value-capture risk**: as disclosed above, SKY's buyback-and-burn rate is governance-directed and could change. This is a property of the *evidence*, not the *architecture*; `ValueCaptureRuleSnapshot`'s correction/supersession lineage (already audited, unmodified) is the correct, existing mechanism to carry a future governance change, and ADR 0022's accounting-period-inside-horizon requirement bounds how stale an accepted rule snapshot may be before Milestone 3's `CanonicalValuationService` may consume it.
- **No live-network test dependency**: all new tests inject a transport/avoid network calls entirely (value-capture acquisition has no network dependency in this codebase's current implementation — the provider only signs and validates operator-supplied payloads), so CI is not coupled to CoinGecko or Sky's documentation site being reachable.
- **Endpoint host accuracy**: `developers.sky.money` and `coingecko.com` listing id `sky` were verified via live web search at the time of this change; source-registry `allowed_hosts` enforcement means an incorrect host would fail closed at acquisition time (an `authorize()` `ValueError`), not silently accept data from an unintended host.
