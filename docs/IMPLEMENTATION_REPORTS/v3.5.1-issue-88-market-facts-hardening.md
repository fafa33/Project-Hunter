# Issue #88 Hardening — Implementation Report

## Status

Implemented on branch `claude/issue-88-market-facts-hardening`, HEAD `41e0c68ef1a5dd6410dffc1446c9e929ddbea66d`.

Issue #88 ("Implement canonical observed market facts foundation") was already closed (completed via PRs #89–#94, independently audited APPROVED in `docs/AUDITS/post-pr93-final-observed-market-facts-audit.md`) before this work began. This is not a reopening of that issue. It implements the two gaps identified in an independent post-remediation architecture analysis of the already-shipped `hunter.market_facts` foundation and its relationship to the `hunter.value_capture` foundation (Issue #95), performed against current `main` HEAD `c12d4f4`. Both gaps were explicitly scoped as low/medium priority, non-blocking follow-up hardening — neither violated Issue #88's or Issue #95's own acceptance criteria as literally written.

## Root Cause

**Gap 1 — hash-format validation.** `raw_payload_hash` on `MarketFactAcquisitionResult`, `ObservedMarketFactRecord`, and `MarketFactAvailabilityEvent` was validated only as non-blank text (`_required_text`), never as a well-formed digest. Issue #88's own acceptance criteria explicitly list "reject... malformed hashes" as a required rejection, and the sibling `hunter.value_capture` foundation (Issue #95) already enforces exactly this kind of format check on its own raw-hash fields via a dedicated `_hash()` validator. No test in the 21-test `market_facts` suite exercised `raw_payload_hash` at all before this change (confirmed by grep).

**Gap 2 — referential integrity between the two completed foundations.** `SupplyBasisSnapshot.observed_market_fact_ids` / `observed_market_fact_versions` (ADR 0021's required linkage from supply-basis evidence to observed market facts) were structurally required to be non-empty, unique, non-blank strings — but nothing in `hunter.value_capture` ever resolved them against real `hunter.market_facts.ObservedMarketFactRecord` entries. A caller could submit a `SupplyBasisSnapshot` referencing a nonexistent fact, a fact belonging to a different entity/asset/representation, or a fact not yet known at the snapshot's own recorded/known time, and the service would accept it silently. Confirmed by direct code inspection: zero references to `market_facts`/`ObservedMarketFact` existed anywhere in `src/hunter/value_capture/*.py` before this change.

## Architectural Decisions

1. **Hash format is domain-specific, not copy-pasted.** `hunter.market_facts` and `hunter.value_capture` use two different raw-hash conventions in production: `market_facts` always produces `"sha256:" + hexdigest` (71 chars, self-describing prefix — confirmed in `CoinGeckoObservedMarketFactProvider` and the `_unavailable()` fallback), while `value_capture` uses bare 64-hex (no prefix). The new `_sha256_hash()` validator in `market_facts/models.py` matches the actual format in production use; it does not reuse `value_capture`'s bare-hex validator, which would have rejected every real hash the CoinGecko provider produces. This was verified empirically before writing any code, not assumed.
2. **The validation only applies to `raw_payload_hash`.** `ObservedMarketFactRecord.content_hash`, and the service-generated `record_id`/`logical_id`/`event_id`/`resolution_id` (all `namespace:sha256:digest`-format, computed internally, never externally supplied) were deliberately left unvalidated by the new check — they are not "raw payload" provenance fields subject to Issue #88's "malformed hashes" criterion, and validating them would conflate an externally-supplied provenance field with an internally-derived identity field.
3. **Cross-domain dependency direction: `value_capture` → `market_facts`, never the reverse.** This preserves the existing layering (`market_facts` is ADR 0021 implementation-order step 1; `value_capture` is step 2 and already depends conceptually on step 1's record family per ADR 0021's evidence-family boundaries). Confirmed no circular import exists (`market_facts` has zero references to `value_capture`).
4. **The market-fact repository dependency defaults from the value-capture repository's own path**, via `market_fact_repository: ObservedMarketFactRepository | None = None` defaulting to `ObservedMarketFactRepository(repository.path)`. Both foundations already share one canonical `data/data_ops.sqlite` generic-SQL store (confirmed identical `DEFAULT_..._DB` constants); deriving the default from the caller's own repository path — rather than hardcoding the production default — is what keeps this correct in test isolation (each test's `tmp_path`-scoped repository automatically gets a matching market-fact repository backed by the same file) without requiring every existing call site to be rewritten.
5. **Validation logic mirrors the existing, already-audited `_require_evidence` pattern exactly** (same five checks: existence, version match, identity compatibility, temporal compatibility via effective/recorded/known-time ordering, and quality/conflict-state gating) rather than inventing a new validation philosophy. This is a deliberate architecture-safety choice: reusing a pattern that has already passed independent audit is lower-risk than a novel one.
6. **No constructor became a hard breaking change in practice.** `market_fact_repository` is optional with a safe, correct default; no existing production call site needed updating. Only test fixtures that construct a `SupplyBasisSnapshot` needed to start referencing a real seeded fact — which is the entire point of the fix, not a side effect to work around.

## Files Changed

- `src/hunter/market_facts/models.py` — added `_sha256_hash()`; applied to `raw_payload_hash` on all three affected dataclasses.
- `tests/test_market_facts_v3_4_0.py` — 4 new tests: malformed/no-prefix/wrong-length hash rejection (`MarketFactAcquisitionResult`), uppercase-hex acceptance, `ObservedMarketFactRecord` rejection, `MarketFactAvailabilityEvent` rejection.
- `src/hunter/value_capture/service.py` — added `market_fact_repository` constructor parameter; added `_require_observed_market_facts()`; wired into `persist_capability` for `SupplyBasisSnapshot` only.
- `tests/test_value_capture_v3_5_0.py` — added `market_fact_registry()` and `seed_observed_market_fact()` fixture helpers; fixed 3 existing tests that previously used placeholder market-fact references to seed and reference real ones; added 5 new tests covering nonexistent reference, version mismatch, identity mismatch, future-known rejection, and future-effective rejection.

No files outside these four were touched. No persistence schema, migration ID, or record-family field was added, removed, or renamed.

## Persistence Impact

None to the schema. Both changes are validation-layer only. `market_facts`' `MARKET_FACTS_SCHEMA_VERSION` and `MARKET_FACTS_MIGRATION_ID`, and `value_capture`'s `VALUE_CAPTURE_SCHEMA_VERSION` and `VALUE_CAPTURE_MIGRATION_ID`, are unchanged. Existing persisted records with well-formed hashes (the only kind any real provider has ever produced) round-trip identically. A hypothetical existing record with a malformed `raw_payload_hash` would now fail to deserialize — no such record was found or is expected to exist, since only the real `CoinGeckoObservedMarketFactProvider` (which always produces well-formed hashes) has ever written to this table in this repository.

## Replay Impact

None to `market_facts`' own strict-known replay semantics — `_sha256_hash()` runs in `__post_init__`, before any replay selection logic, and rejects malformed input at construction/deserialization time rather than during cutoff filtering.

For `value_capture`, `_require_observed_market_facts()` is a **write-time** authorization check (inside `persist_capability`, before persistence), not a read-time replay filter — it does not change `strict_known_supply`'s selection semantics, which were verified unchanged (byte-identical to the pre-change version; only the new `strict_known_evidence` addition from the prior PR #105 work and this turn's untouched `_strict_known` helper remain in play).

## Migration Impact

None. No migration ID changed on either domain. No backfill is required or performed. Existing well-formed records are unaffected on read.
