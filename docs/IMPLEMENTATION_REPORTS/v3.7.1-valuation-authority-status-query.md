# Issue #107 — Read-only `status` query for `hunter valuation-authority` — Implementation Report

## Status

This report documents a narrow, read-only addition to the existing `hunter valuation-authority` production entry point (`src/hunter/valuation_authority/command.py`, introduced by PR #131 / commit `898879f`). It does not implement, resume, or unblock Milestone 5. It does not close Issue #107.

## Why this change

A focused review of Issue #107's current state (Milestones 1–4 merged, production entry point merged, all confirmed via `git log`, direct inspection of `data/data_ops.sqlite`, and `docs/IMPLEMENTATION_REPORTS/v3.7.0-milestones-2-4-canonical-valuation-and-production-entry-point.md`) found:

- All four in-scope milestones and the production entry point (`hunter valuation-authority run MANIFEST.json`) are already implemented, merged, and tested.
- The real, currently-persisted Sky evidence chain still has a 30-day accounting period (not the required 365) and no populated `amount`/`rate_or_proportion` — independently re-confirmed by direct inspection of the tracked `data/data_ops.sqlite` (records `57ddd15569f7348f72b6a0498fd8fff6d0fae0e61d0906f856625cc9ed2e5e47` and `f774f946b80c11244faddeb69f4d40e01a501226c036df5497bc3dbc00020abd`). This is a disclosure-architecture/evidence-availability constraint, not a code defect — it is the exact problem `ADPR-0002` was created to enumerate options for, and resolving it requires a future decision this session is not authorized to make.
- Acquiring a genuinely different, qualifying (exact-365-day, populated amount+rate) real disclosure is not achievable from this session: the outbound network proxy denies `api.coingecko.com` (reproduced directly: `CONNECT tunnel failed, response 403`), and inventing or approximating one would violate Constitutional Rule 2 and this issue's explicit no-fabrication requirements.

Given this, the real qualifying-evidence blocker cannot be unblocked by implementation. A separate, smaller, permitted gap was identified instead: **neither `hunter valuation-evidence` nor `hunter valuation-authority` exposes any read-only query surface.** Both CLI entry points are write-only (`acquire`, `run` for `methodology`/`estimate`). Verifying persisted `ValuationMethodologySnapshot`/`FairValueEstimateRecord`/`ValuationAssessmentRecord` state today requires either running the full pytest suite or writing ad hoc Python against the repositories directly (as this review itself had to do). This directly undermines:

- Issue #107 Milestone 1's own acceptance criterion ("independently verifiable... via the existing strict-known read APIs" — the Python API exists, but nothing operator-facing invokes it);
- Issue #135 Finding 1's required completion step 4 ("Independently query and strict-known replay the resulting methodology, fair-value estimate, and assessment records");
- Issue #107's own Required Delivery Sequence step 6 (a future independent post-merge audit needs a reproducible way to verify state).

Closing this gap is the smallest permitted step that adds real value without redefining architecture, fabricating evidence, or touching Milestone 5's blocked scope.

## What this change adds

A `status` operation on the existing `hunter valuation-authority run MANIFEST.json` entry point (no new CLI verb, no new package — the manifest's `operation` field already routes between `methodology`/`estimate`; `status` is a third route through the same dispatch).

```json
{"operation": "status", "target": "methodology", "effective_as_of": "...", "known_by": "..."}
{"operation": "status", "target": "fair_value_estimate", "effective_as_of": "...", "known_by": "...", "logical_id": "..."}
{"operation": "status", "target": "valuation_assessment", "effective_as_of": "...", "known_by": "...", "logical_id": "..."}
```

Output: `{"available": false}` when no strict-known-eligible record exists at the requested cutoff, or `{"available": true, "record": {...}}` with the full record serialized (JSON-safe datetimes), when one does.

### Architecture impact

None. No ADR is touched. No existing validation, formula, replay, or persistence logic is added, modified, or duplicated. `_status` calls exactly the same repository read methods the existing test suite already exercises directly — `ValuationMethodologyRepository.strict_known_methodology`, `CanonicalValuationRepository.strict_known_fair_value_estimate`, `CanonicalValuationRepository.strict_known_valuation_assessment` — and returns their result unmodified (JSON-serialized). It performs no writes, no authorization decisions, and no interpretation of the data. This mirrors the read-only projection role ADR 0016 assigns to Dashboard API: it may display authoritative records and explicit unavailable states, and never establishes authority, calculates a result, or repairs missing data.

### Authority boundaries preserved

- `CanonicalValuationRepository`/`ValuationMethodologyRepository` still expose no public write method (unchanged; verified by the existing `test_repository_bypass_remains_impossible`, which the new operation does not touch).
- No new dependency on `CanonicalValuationService` or `CanonicalValuationMethodologyAuthority` — `status` reads only, so it does not construct either service.
- No caller-supplied value can select "latest"/"current" state: `status` requires the same explicit `effective_as_of`/`known_by` (and `logical_id`, for the two valuation targets) the write operations already require, resolved by the same strict-known repository logic.

## Test coverage

`tests/test_valuation_authority_v1.py`, section M (7 new tests):

- `status` reports `available: false` before any methodology has been persisted.
- `status` reports a persisted methodology, matching a direct repository read (`content_hash` cross-checked).
- `status` reports `available: false` for `fair_value_estimate`/`valuation_assessment` before either has been created.
- `status` reuses genuine strict-known cutoff resolution, not a "latest" shortcut: queried at a `known_by` before a correction, it returns the original estimate; queried at/after the correction's `known_at`, it returns the correction (mirrors the existing direct-repository proof in section E, now proven through the CLI).
- `status` reports a persisted `ValuationAssessmentRecord`, with `fair_value_estimate_record_id` cross-checked against the estimate that produced it.
- An unknown `target` value is rejected with a clear `ValueError`.
- `status`, run repeatedly, never itself writes or mutates a record (row count before/after is compared across three repeated queries).

**Unaffected by this change, and not claimed to be resolved by it.** This change is purely a read-only operability addition. It does not, and cannot, supply real qualifying evidence:

- The real, currently-persisted Sky `FundamentalEvidenceRecord` still has a 30-day accounting period and `amount: None`.
- The real, currently-persisted Sky `ValueCaptureRuleSnapshot` still has `rate_or_proportion: None`.
- `data/data_ops.sqlite` is untouched by this change (verified: restored after an incidental, unrelated test-run side effect — see Verification Results below — and confirmed via `git diff` to carry no changes in the final commit).

Requirement 9 still awaits exactly what `v3.7.0`'s report already identified: real, disclosed, exact-365-day Sky (or another qualifying entity's) evidence with a populated amount and rate, which this change does not and cannot provide. Acquiring it depends on either a future decision selecting among `ADPR-0002`'s enumerated disclosure-architecture-classification options, or discovery and independent verification of a genuinely different qualifying real disclosure — neither of which this session is authorized or positioned to perform.
