## Authority Flow

```text
Registered Evidence Source (RegisteredValueCaptureProvider)
→ SupplyAndValueCaptureService (sole write authority; private persist_capability closure)
→ hunter.persistence.sql (generic SQL authority; SnapshotRecord envelope)
→ data/data_ops.sqlite
```

The service owns registry authorization (`ValueCaptureSourceRegistry`),
receipt signature/hash verification, canonical identity enforcement,
evidence linkage (`_require_evidence`), deterministic logical/content-hash
identity, conflict-policy flagging, correction authorization (including
authority-tier downgrade rejection), and write-plan authorization. It
exposes no public writer factory: the write path is a closure bound only
inside `SupplyAndValueCaptureService.__init__` and reachable solely through
`ingest_evidence` / `ingest_supply` / `ingest_rule`.

The repository (`SupplyAndValueCaptureRepository`) is a read/persistence
adapter over the shared generic SQL snapshot store. It performs no
validation and exposes no direct write method — persistence happens only
through the service's internal capability.

## Record Families

- `FundamentalEvidenceRecord`
- `SupplyBasisSnapshot`
- `ValueCaptureRuleSnapshot`

All three are immutable frozen dataclasses (`src/hunter/value_capture/models.py`)
under schema version `VALUE_CAPTURE_SCHEMA_VERSION = "supply-value-capture-v3.5.0"`
(the schema-version string itself was not renamed for v3.5.1 — it identifies
the on-disk payload contract, which is additive/backward-incompatible-checked
via explicit required-field validation in `repository.py`, not tied to sprint
numbering). Each record carries deterministic `record_id`/`logical_id`,
semantic version, full `EconomicClaimIdentity` (entity, economic claim,
asset, representation, token, optional chain/contract), effective/recorded/
known times, confidence/uncertainty, quality/conflict state, source/parser
provenance, a raw content hash, and correction/supersession lineage
(`supersedes_record_id` + `correction_reason`, always provided together).

## Persistence

Default database:

- `data/data_ops.sqlite` (Hunter's canonical generic SQL authority — no
  standalone value-capture database exists)

Migration identifier:

- `generic-sql-fundamental-value-evidence-v1`
  (`VALUE_CAPTURE_MIGRATION_ID` in `repository.py`)

Storage mechanism:

- All records and acquisition receipts are persisted as `SnapshotRecord`
  payloads (`hunter.persistence.records.SnapshotRecord`) in the shared
  `persistence_records` table, distinguished by `snapshot_type`
  (`fundamental-evidence`, `supply-basis`, `value-capture-rule`,
  `fundamental-value-evidence-acquisition-receipt`). There are no
  domain-specific SQL tables named `fundamental_evidence_records`,
  `supply_basis_snapshots`, or `value_capture_rule_snapshots` — those names
  are logical table identifiers used only by
  `SupplyAndValueCaptureRepository.count()` for test/diagnostic counting,
  mapped internally to the shared snapshot store.

Persistence guarantees (all independently tested):

- **Insert-or-identical idempotency**: re-persisting a record or receipt
  with the same deterministic ID and identical content is a no-op that
  returns the existing row. Enforced by the generic layer
  (`hunter.persistence.sql.repositories.base.SQLRecordRepository.save`).
- **Divergent-duplicate rejection**: the same ID with different content
  raises `PersistenceIdentityConflictError`, translated to
  `ValueCaptureIntegrityError` at the value-capture boundary, and the
  surrounding write transaction is rolled back.
- **Append-only correction lineage**: a correction must reference an
  existing predecessor of the same snapshot type and logical ID, with a
  strictly later `recorded_at`/`known_at`; branching (two corrections
  claiming the same predecessor) is rejected.
- **Atomicity**: the acquisition receipt and its derived record are written
  in one `BEGIN IMMEDIATE` transaction per ingestion call, so a repository
  read never observes a receipt without its record or vice versa.
- **Strict-known point-in-time reads**: `strict_known_supply`,
  `strict_known_rule`, and `strict_known_evidence` (added in PR #105) each
  select, for an exact entity/claim/representation/category scope, the
  single current (non-superseded), accepted, non-open/contested record
  whose `effective_at <= effective_as_of` and `recorded_at, known_at <=
  known_by` — with no latest/current fallback. `strict_known_rule`
  additionally enforces the rule's `applicability_start/end` window; the
  other two families have no analogous validity window.
- **Deterministic logical-history reads**: `evidence_history`,
  `supply_history`, and `rule_history` return the complete append-only
  chain for a logical ID in stable ascending
  `(effective_at, recorded_at, known_at, record_id)` order.
- **Unresolved-conflict queries**: `unresolved_evidence_conflicts`,
  `unresolved_supply_conflicts`, and `unresolved_rule_conflicts` return the
  current (non-superseded) records left in `open`/`contested` state,
  deterministically ordered.

## Conflict Detection

`SupplyAndValueCaptureService._apply_conflict_policy` flags a newly
persisted record as `conflict_state="open"` when it diverges in substance
(any field outside a small bookkeeping exclusion set) from another current,
`accepted` record sharing the same logical ID and `effective_at`, excluding
the record's own correction predecessor. This mirrors
`hunter.market_facts.ObservedMarketFactService`'s conflict policy. No
winner is selected and no averaging occurs — both records persist, and the
divergence is surfaced only through the unresolved-conflict query surface.

## Registry

Source registrations: `configs/value_capture_sources.yaml`. Each source
declares `source_id`, `authority_tier`, `source_type`, `allowed_hosts`,
`endpoint_patterns`, `parser_version`, `capabilities`, `enabled`, and
optional `correction_predecessor_tiers`. `ValueCaptureSourceConfig.authorize`
enforces enabled state, exact parser version, capability membership, HTTPS
scheme, allow-listed host, and endpoint-pattern prefix before any
acquisition is accepted. `authorize_correction_transition` rejects a
correction whose successor source's authority tier would downgrade the
predecessor's.

## Replay

Strict-known selection (see Persistence above) requires exact identity
scope match, `effective_at <= effective_as_of`, `recorded_at <= known_by`,
`known_at <= known_by`, `quality_state == "accepted"`, and
`conflict_state in {"none", "resolved"}`. There is no latest fallback,
current-state fallback, manual fallback, post-cutoff substitution, or
cross-representation substitution.

## Explicit Exclusions Preserved

This implementation does not activate or modify:

- fair value; intrinsic value; valuation methodology;
- comparative valuation; peer selection;
- mispricing; asymmetry;
- Opportunity scoring or ranking; Portfolio Intelligence;
- Dashboard-side calculations;
- Market Validation formulas, weights, Timing, committee, reports, or
  scalar inputs.

The Market Validation inputs `valuation`, `comparative_valuation`,
`mispricing`, and `asymmetry` remain unavailable. No file under
`src/hunter/market_validation/` imports `hunter.value_capture`.

## Known Limitations

- Rule-to-evidence pathway binding validates identity, provenance, quality,
  and chronology of referenced evidence, but does not independently verify
  that the referenced evidence's `evidence_type` is semantically capable of
  establishing the specific cash-flow mechanism a rule claims (e.g. a
  `fee_distribution` rule referencing `governance_record` evidence rather
  than a disclosure that actually states a fee flow). Full pathway
  semantics are reserved for the future valuation-methodology work
  (ADR 0021 implementation-order step 3 onward) and are explicitly out of
  scope for this evidence-foundation issue.
- `configs/value_capture_sources.yaml` registers one enabled onchain source
  (`verified-onchain-value-capture`, `ethereum.publicnode.com`); its
  real-world acquisition behavior is outside the scope of this record/
  persistence-layer remediation and was not exercised by these tests.
