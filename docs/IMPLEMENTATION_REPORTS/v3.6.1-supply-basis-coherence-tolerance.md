# Supply Basis Coherence Tolerance — Implementation Report

## Status

Implemented on branch `fix/supply-coherence-tolerance`, built on `main` HEAD `2772c9c` (PR #116/#117 merged).

## Root cause

`SupplyBasisSnapshot.__post_init__` (`src/hunter/value_capture/models.py`) previously hard-rejected any
`quantity_components` where `total_supply > fully_diluted_supply`, raising
`ValueError("total supply must not exceed fully diluted supply")` and refusing to persist the record at all.

This was found to reject real, live provider data. CoinGecko's `market_data` for Sky (SKY) reported, in
the same API response snapshot:

```
circulating_supply = 23355983976.864086
total_supply       = 23462665147.36596
max_supply         = 23462665147.3
```

`total_supply` exceeds `max_supply` (the source of `fully_diluted_supply`) by `0.06596` — a relative gap
of `~2.8×10⁻¹²`. This is provider rounding/caching/asynchronous-field-publication noise, not a real
economic contradiction (Sky has not exceeded its own disclosed maximum supply). The prior model offered
exactly one way to persist anything in this situation: omit `fully_diluted_supply` from the snapshot
entirely (the interim fix shipped in PR #117's `scripts/acquire_sky_supply_basis.py`). That interim fix
was itself flagged by independent review (Codex) as insufficient: ADR 0022 Scope condition 3 requires
circulating, total, *and* fully diluted supply to each be independently observable, and an omitted
component cannot satisfy that.

The actual root cause is architectural: the canonical model conflated "this provider observation is
numerically inconvenient" with "this provider observation must be discarded." Those are not the same
thing, and this repository's own established pattern elsewhere in this exact record family
(`SupplyAndValueCaptureService._apply_conflict_policy`, which flags divergent duplicate submissions via
`conflict_state="open"` rather than rejecting them) already demonstrates the correct alternative: surface
an issue through `conflict_state`, don't silently discard the observation, and never reject well-formed
provider data outright.

## Architecture rationale

Two categories of `total_supply > fully_diluted_supply` are distinguished, both **without** rejecting
persistence in either case:

1. **Provider precision/timing noise** — the gap is small relative to the values themselves. Persisted as
   ordinary accepted data, exactly as observed, no flag.
2. **A real, larger contradiction** — persisted with both raw values intact, but `conflict_state` is
   auto-elevated to `"open"` (only if the caller supplied `"none"` — an explicit non-`"none"` value from
   the caller, e.g. an already-`"resolved"` correction, is respected and left alone), so the incoherence is
   visible to every downstream consumer rather than silently swallowed.

The dividing line is `SUPPLY_COHERENCE_RELATIVE_TOLERANCE = Decimal("0.0001")` (0.01% relative gap between
`total_supply` and `fully_diluted_supply`). This constant is:

- **Entity-agnostic and provider-agnostic.** It is applied uniformly to whatever `quantity_components` are
  present, with no reference to Sky, CoinGecko, or any other named entity/provider anywhere in the check.
- **Not tuned to Sky's specific numbers.** Sky's actual observed relative gap (`~2.8×10⁻¹²`) is roughly
  eight orders of magnitude below the tolerance — it was not reverse-engineered to just barely pass.
- **A relative, not absolute, threshold**, so it scales correctly across supply magnitudes from small-cap
  to trillion-unit tokens alike.

Raw provider values are never overwritten, normalized, clamped, fabricated, substituted, or inferred:
`quantity_components` always stores exactly what the caller supplied (unchanged, `str`-typed Decimal
literals), for both the small-gap and large-gap cases. Only `conflict_state` — already a first-class,
caller-suppliable field on this record family, not a new concept — is conditionally adjusted, and only in
the large-gap case, and only when the caller left it at the default `"none"`.

## Exact invariant change

`src/hunter/value_capture/models.py`:

- Added module-level constant `SUPPLY_COHERENCE_RELATIVE_TOLERANCE = Decimal("0.0001")`.
- In `SupplyBasisSnapshot.__post_init__`, replaced the unconditional
  `raise ValueError("total supply must not exceed fully diluted supply")` with a tolerance check:
  `relative_gap = (total - diluted) / diluted` (guarding `diluted == 0` as always "beyond tolerance"); if
  `relative_gap` is `None` or exceeds the tolerance, `conflict_state` is elevated to `"open"` (only if it
  was `"none"`); otherwise nothing changes. **No exception is raised in either branch.**

No other coherence check in the same method (`circulating <= total`, `locked <= total`,
`excluded/treasury_held <= total`) was touched — those have not been shown to have any real-world
violation, and loosening them was not requested or evidenced; narrowing the change to the one check with a
demonstrated real-data failure avoids unscoped architecture drift.

`scripts/acquire_sky_supply_basis.py`: `build_supply_payload` now unconditionally includes
`fully_diluted_supply` (from the observed `max_supply` fact, verbatim) whenever `max_supply` was returned
by the provider — the script no longer pre-filters or omits it based on coherence; that policy decision now
lives exclusively in the canonical model, which is the single place it should be enforced. The now-unused
`Decimal` import (used only by the removed pre-filter) was removed.

## Migration

None required. This is a validation-logic change to an in-memory `__post_init__` check; the persisted row
shape, `VALUE_CAPTURE_SCHEMA_VERSION`, and `MARKET_FACTS_MIGRATION_ID`/`VALUE_CAPTURE_MIGRATION_ID` are all
unchanged. Every previously-accepted `SupplyBasisSnapshot` necessarily had `total <= fully_diluted` already
(the strict form of the now-relaxed check), so relaxing the check cannot invalidate any existing persisted
record — full replay compatibility is preserved by construction. `ADR 0022`'s authority boundaries,
append-only correction semantics, and strict-known replay guarantees are all untouched by this change; no
service, repository, or authorization logic was modified — only the record's own `__post_init__` validation.

## Known limitations / residual risk

- The `0.0001` (0.01%) relative tolerance is a considered, defensible, entity-agnostic policy choice, not a
  value derived from a formal statistical model of CoinGecko's rounding behavior — no such model exists to
  derive it from. It is documented in-line in `models.py` and easy to revisit if a future provider's
  legitimate precision noise exceeds it, or if a future entity's real economic discrepancy falls within it
  (in which case it would now be silently accepted as "noise" rather than flagged — an inherent tradeoff of
  any fixed tolerance, disclosed here rather than hidden).
- This fix does not retroactively correct the `SupplyBasisSnapshot` already persisted for Sky on PR #110's
  branch during PR #117-era acquisition (which has no `fully_diluted_supply` component, per the interim
  omission fix). A fresh acquisition run against the corrected `main` (once this fix merges) is required to
  produce a new, complete `SupplyBasisSnapshot` with all three coherent quantities.
