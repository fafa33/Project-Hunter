# ADR 0028: Canonical Evidence Assembly Supporting Authorities

## Status

Proposed.

Governing preparation record: [ADPR-0005 — Canonical Evidence Assembly Supporting Authorities](../architecture-records/ADPR-0005-evidence-assembly-supporting-authorities.md). This is revision 4 of both records, produced across three independent hostile architecture review rounds against Draft PR #192 (tracked under Issue #191): round 1 (five `CHANGES REQUIRED` findings against revision 1, resolved in revision 2), round 2 (four `CHANGES REQUIRED` findings against revision 2, resolved in revision 3), and round 3 (three `CHANGES REQUIRED` findings against revision 3, resolved in this revision). Revision 1 left four material questions open (OQ-001 through OQ-004) and split Methodology Contract ownership ambiguously between `hunter.valuation_methodology` and a possible new sibling package; revision 2 resolved those with a singular design. Round 2 found that design's normative detail was, in four specific places, either unexecutable against the real `src/` API it claimed to use, internally self-contradictory, or incompletely specified; revision 3 fixed all four. Round 3 found revision 3's governing-snapshot check still used the wrong strict-known coordinate (making it unable to detect a later-effective disabling successor), found `value_capture_pathway_id` asserted in prose and in the `contract_id` hash formula but never added as an actual dataclass field, and found `AssembledFundamentalEvidenceRecord` still lacked any persisted field capable of reconstructing which exact evidence-semantics classification and ruleset version each constituent was validated against. This revision (4) fixes all three without altering the architecture round 3 otherwise confirmed.

Neither this ADR nor ADPR-0005 has been independently accepted. This ADR is drafted for a fourth round of independent architecture review and carries no authority until both records are separately accepted. It does not authorize implementation of any of the three authorities it defines, does not resume Issue #190 (which remains `BLOCKED`), and does not activate any Market Validation input. It does not modify `CanonicalEvidenceAssemblyService`'s or `CanonicalValuationMethodologyAuthority`'s existing validation invariants, ordering, or behavior for any currently-reachable code path (both remain production-unreachable today because none of the three supporting authorities has a production implementation — see ADPR-0005 E-003/E-004). It does, however, require five narrowly bounded, explicitly enumerated *additive* signature or call-site changes to that same already-accepted, currently-dormant code, all of which are future implementation work this ADR authorizes but does not itself perform (this PR touches no file under `src/`) — see "Exact, bounded additions to already-accepted `hunter.evidence_assembly` code," below, added by this revision precisely so no such change is left implicit, silently assumed executable, or discovered later by an implementer.

## Context

ADR 0025 (Accepted) establishes the Canonical Evidence Assembly Authority and fully specifies what three supporting collaborators must validate before `assemble()` may produce an `AssembledFundamentalEvidenceRecord`. `docs/ARCHITECTURE_AUDITS/issue-190-evidence-assembly-authority-gap.md` and ADPR-0005 confirm none of the three — Methodology Contract, Evidence Shape Registry, Evidence Semantics — has a production implementation.

Revision 1 of this ADR resolved Evidence Shape Registry ownership (reaffirming ADR 0025's own explicit text) but left Methodology Contract's scope and Evidence Semantics' authoring model as open questions, and proposed a Methodology Contract design (a standalone sibling record under `hunter.valuation_methodology`, without fully specifying its relationship to `ValuationMethodologySnapshot`) that independent review correctly identified as incomplete against ADR 0025's own accepted text: ADR 0025's "Exact amendment to ADR 0022" states "a future `ValuationMethodologySnapshot` version may declare acceptance" of assembled evidence — a sentence revision 1 acknowledged (as Open Question OQ-004) but did not resolve.

This revision resolves that tension by direct inspection of the already-accepted, unmodifiable code both the contract-consuming and methodology-owning services already run: `CanonicalEvidenceAssemblyService.assemble()`'s `_validate_methodology_contract` (`src/hunter/evidence_assembly/service.py:339-387`) checks a fetched `MethodologyEvidenceInputContract`'s `entity_id`, `representation_id`, `currency`, `unit`, `accounting_window_start`, and `accounting_window_end` against the *specific target* being assembled — fields `ValuationMethodologySnapshot` structurally cannot carry as single values, since one methodology snapshot is consumed across every entity `CanonicalValuationService` ever values (`src/hunter/valuation_methodology/models.py:44-71` carries no entity or window scope at all). This is not an implementation preference; it is a fact about code this ADR is not authorized to change. The design below is the single, exact resolution that satisfies both that structural fact and ADR 0025's literal text.

## Decision

Hunter establishes two new supporting authorities. `MethodologyEvidenceInputContract` (Methodology Contract) and `AuthoritativeEvidenceSemantics` (Evidence Semantics) each get one exact, singular design below, with no alternative left open. `EvidenceShapeRegistry` is unchanged from revision 1.

### Methodology Contract Authority

**Resolved scope: per-target, exactly.** One `MethodologyEvidenceInputContract` record declares acceptance for exactly one `(governing methodology version, entity, representation, value-capture pathway, currency, unit, accounting window)` combination. This is not a design preference — it is required by `_validate_methodology_contract`'s existing, unmodifiable field-by-field comparison against the specific target being assembled (`service.py:372-387`), and by the `strict_known_contract(*, contract_id, contract_version, known_by)` protocol's already-fixed signature (`service.py:41-44`), which carries no target parameter a global declaration could be resolved against.

**Resolved activation/declaration split.** Two records jointly control eligibility, with one unambiguous activation authority:

1. `ValuationMethodologySnapshot` gains one new field, `accepts_assembled_evidence: bool` (default `False` on every existing and future snapshot that does not explicitly set it). This is the **sole activation authority** — conforming exactly to ADR 0025's literal text that "the `ValuationMethodologySnapshot` in force explicitly declares acceptance of assembled evidence." No per-target contract may be authored, and none may be returned as strict-known, for a governing snapshot whose `accepts_assembled_evidence` is not `True` at the same replay cutoff.
2. `MethodologyEvidenceInputContract` — a new, per-target sibling record family — is the **declaration instance**: it states, for one exact target, "the exact requirements under which [the methodology] accepts [assembled evidence]" (the same ADR 0025 sentence's second clause). It exists only in reference to, and only when authorized by, an in-force snapshot with `accepts_assembled_evidence = True`.

**Resolved cross-reference.** The contract references the snapshot, never the reverse: every `MethodologyEvidenceInputContract` carries `governing_methodology_record_id`, `governing_methodology_logical_id`, and `governing_methodology_semantic_version`, naming the exact `ValuationMethodologySnapshot` it was authored under. `ValuationMethodologySnapshot` carries no list of, or reference to, any contract — an immutable snapshot does not grow a mutable back-reference list as targets are added over time.

**Resolved conflict/disagreement behavior — exact, executable mechanism (resolves round-2 Finding 1; corrects a round-3 defect in that resolution).** `CanonicalValuationMethodologyAuthority`'s real, existing public API is exactly `get(record_id) -> ValuationMethodologySnapshot | None`, `strict_known_methodology(*, effective_as_of: datetime, known_by: datetime) -> ValuationMethodologySnapshot | None` (`service.py:142-154`), and `methodology_history(logical_id)`. It does **not** accept a `record_id` or `record_version` parameter on `strict_known_methodology` — a governing-snapshot check cannot look up an arbitrary historical record by ID through that method alone.

Revision 3 resolved round 2's Finding 1 by calling `strict_known_methodology(effective_as_of=snapshot.effective_at, known_by=known_by)` — using the *contract's referenced snapshot's own* `effective_at` as the query's `effective_as_of` bound. Independent review's third round correctly identified this as still wrong, for a reason distinct from round 2's finding: because `_strict_known`'s selection (`service.py:214-231`) filters candidates by `effective_at <= effective_as_of`, passing `snapshot.effective_at` as the bound permanently excludes any successor whose own `effective_at` is *later* than `snapshot.effective_at` — by construction, no query built this way can ever observe a later-effective successor, including one that sets `accepts_assembled_evidence` back to `False`. Revision 3's own text said as much, treating it as intended behavior ("a later correction with a later `effective_at` cannot win this query"); it is not intended behavior — it silently narrows "the snapshot in force" to "the snapshot in force as of its own effective time," which is not what "in force at the assembly decision" means, and it is exactly the gap round 3 exploited.

**The fix is a coordinate substitution, not a new algorithm shape.** Methodology eligibility must be evaluated at the **assembly's own decision coordinates** — the same `effective_as_of`/`known_by` pair that governs every other strict-known selection `assemble()` performs for that same call — never at the referenced snapshot's own `effective_at`. Within `assemble()`, those coordinates already exist and are already named: `accounting_window_end` is, by ADR 0025's own already-accepted "Temporal authority" table, the exact moment "the composed economic interval becomes fully observed," and is required to equal the constructed record's own `effective_at` (`AssembledFundamentalEvidenceRecord.__post_init__`, `models.py:250-251`: `"effective_at must equal accounting_window_end"`); `replay_cutoff` is the single `known_by` coordinate already threaded into every other strict-known call `assemble()` makes (`evidence_shape_registry_authority.strict_known_registry(..., known_by=replay_cutoff)`, `evidence_semantics_authority.strict_known_semantics(..., known_by=replay_cutoff)`). These two — `accounting_window_end` as `effective_as_of`, `replay_cutoff` as `known_by` — are "the assembly's own decision coordinates."

The existing `MethodologyContractAuthority.strict_known_contract` Protocol (`service.py:41-44`) does not currently accept an `effective_as_of` parameter at all — of every strict-known selector in this codebase (`strict_known_methodology`, `AssembledFundamentalEvidenceRecord.strict_known`, and this ADR's own `strict_known_registry`/`strict_known_semantics`/`strict_known_ruleset`), it is the sole exception carrying only a `known_by` coordinate. This is precisely why revision 3 substituted `snapshot.effective_at` in the first place: no other coordinate was reachable inside `strict_known_contract`'s existing signature. ADR 0025's own Compatibility row for ADR 0020 states strict-known replay "already governs any immutable persisted record selected for canonical input assembly generically" — a single-coordinate `known_by`-only Protocol is not that; it is a pre-existing gap between what ADR 0025 already requires and what the Protocol's signature actually provides, not a new invention of this revision. Closing it requires one additive parameter; see "Exact, bounded additions to already-accepted `hunter.evidence_assembly` code," below, for the full, explicit statement of that (and every other) required signature change, none of which this ADR or this PR performs.

With `effective_as_of` and `known_by` both available as caller-supplied parameters, `CanonicalValuationMethodologyAuthority.strict_known_contract(*, contract_id, contract_version, effective_as_of, known_by)` (see "Exact canonical service owner," below) resolves the governing snapshot using only the real, existing `get`/`strict_known_methodology` API, in this exact sequence — explicitly distinguishing the two kinds of lookup round-3 Finding 1 requires kept distinct:

1. **Direct exact-record retrieval, used to verify persisted provenance.** Fetch the exact referenced snapshot by identity: `snapshot = self.get(governing_methodology_record_id)` (the contract's own stored provenance field, defined below). If `snapshot is None`, or `snapshot.logical_id != governing_methodology_logical_id`, or `snapshot.semantic_version != governing_methodology_semantic_version`, the contract is ineligible — return `None`. This step only confirms the contract's own stored claim about which snapshot it was authored under; it makes no statement about what is *in force now*.
2. **Strict-known resolution, used to identify the snapshot actually in force at the assembly decision coordinates.** Call `in_force = self.strict_known_methodology(effective_as_of=effective_as_of, known_by=known_by)` — the caller-supplied assembly coordinates, **never** `snapshot.effective_at`. Because `_strict_known` filters by `effective_at <= effective_as_of` and `recorded_at <= known_by`/`known_at <= known_by`, then sorts eligible, non-superseded candidates by `(effective_at, recorded_at, known_at, record_id)` descending, this call returns exactly the snapshot that is actually in force at the moment the assembled record itself becomes effective, as of what is knowable at the replay cutoff — including any successor whose `effective_at` falls between `snapshot.effective_at` and `effective_as_of`, which step 2 of revision 3's algorithm could never see.
3. The contract is eligible only if `in_force is not None`, `in_force.record_id == governing_methodology_record_id` — the snapshot actually in force at the assembly's own coordinates is *exactly* the one the contract names, not merely a same-lineage descendant of it — and `in_force.accepts_assembled_evidence is True`.

If any step fails, `strict_known_contract` returns `None`; `assemble()`'s existing, unmodified code already treats a `None` return as `CanonicalEvidenceAssemblyError("no exact strict-known methodology evidence contract")` (`service.py:109-110`). This is fail-closed, not a new failure mode. It closes every case round-3 Finding 1 named:

- **A later-effective successor disables assembled evidence.** For any assembly whose `effective_as_of` (`accounting_window_end`) is at or after the successor's own `effective_at`, step 2 resolves `in_force` to that successor (or a later one); step 3's identity check fails because `in_force.record_id != governing_methodology_record_id` (or, if it does match by coincidence, `in_force.accepts_assembled_evidence` reflects the successor's own value) — the contract becomes ineligible starting exactly at the successor's effective time, never before.
- **Historical replay before the successor's effective time.** For an assembly whose `effective_as_of` is strictly before the successor's `effective_at`, the successor fails `_strict_known`'s `effective_at <= effective_as_of` bound and is excluded from the eligible set entirely; `in_force` resolves to `snapshot` (or an earlier-still predecessor), and the contract remains eligible exactly as it did before the successor existed — replay is unaffected by a correction that had not yet taken effect at the replayed coordinates.
- **Corrections known only after the replay `known_by` cutoff never leak backward.** `_strict_known`'s `recorded_at <= known_by`/`known_at <= known_by` filter excludes any successor that was not yet *knowable* at the requested cutoff, independent of its `effective_at` — a successor recorded or known after `known_by` cannot appear in `in_force`'s candidate set regardless of how far in the "past" its declared `effective_at` is.
- **The contract and snapshot are always resolved at the same strict-known coordinates.** Both `strict_known_contract`'s own contract-level bitemporal check (unchanged from revision 3, below) and step 2's governing-snapshot check consume the identical, single `(effective_as_of, known_by)` pair supplied by the one caller — there is no second, drifting cutoff either resolution could use.

**Resolved exact canonical service owner: `CanonicalValuationMethodologyAuthority`** (`src/hunter/valuation_methodology/service.py:36`), not a new service and not a new package. It gains two new public methods: `persist_evidence_input_contract(...)` (authoring) and `strict_known_contract(*, contract_id: str, contract_version: str, effective_as_of: datetime, known_by: datetime) -> MethodologyEvidenceInputContract | None` (retrieval). Revision 3 stated this method's signature as satisfying `MethodologyContractAuthority`'s protocol "without modification" to `hunter.evidence_assembly.service`; that claim is corrected here — the protocol itself must additively gain the `effective_as_of` parameter shown above, exactly as authorized in "Exact, bounded additions to already-accepted `hunter.evidence_assembly` code," below, so that `strict_known_contract`'s new implementation and its Protocol declaration agree. One service already owns `ValuationMethodologySnapshot`'s strict-known resolution; giving the cross-check above to a second, different service would duplicate that resolution logic and violate Constitutional Rule 5 (Single Source of Truth). This resolves former Open Question OQ-003 definitively: not a new sibling service.

**Resolved exact repository owner: `ValuationMethodologyRepository`** (`src/hunter/valuation_methodology/repository.py:23`), extended with a new table and mechanical methods for `MethodologyEvidenceInputContract`, not a new repository class and not a new package. `AssembledEvidenceRepository` already establishes the precedent of one repository class owning two related record families (`AssembledFundamentalEvidenceRecord` and `AssemblyConflictRecord`) in this same codebase (`src/hunter/evidence_assembly/repository.py`); this ADR applies the identical, already-audited pattern.

**Resolved authorship-governance boundary.** A `MethodologyEvidenceInputContract` may be authored only through `CanonicalValuationMethodologyAuthority.persist_evidence_input_contract`, by whatever governance process is already authorized to call `CanonicalValuationMethodologyAuthority.persist_methodology` for corrections to the methodology itself (this ADR does not change who that is — it is an existing, out-of-scope operational-authorization question, unchanged from ADR 0022). It is never authored by `CanonicalEvidenceAssemblyService`, by an `assemble()` caller, or by any Evidence Assembly-side code — preserving the dependency direction fixed below.

**Package ownership and dependency direction (resolves Finding 5).** The entire Methodology Contract Authority — construction, validation, authorization, persistence, versioning, correction — is exclusively owned and performed by `hunter.valuation_methodology`: one service (`CanonicalValuationMethodologyAuthority`), one repository (`ValuationMethodologyRepository`). No part of that ownership is split with, delegated to, or shared with `hunter.evidence_assembly`.

*Dependency direction, precisely stated.* `hunter.evidence_assembly.service` (the consumer) never imports `hunter.valuation_methodology` at all: `MethodologyContractAuthority` is a `typing.Protocol`, already defined there and unchanged by this ADR, and Python `Protocol`s are structurally typed — a class satisfies one by shape, without the protocol's module ever importing the implementing class. So the business-logic and service-level dependency is unambiguously one-directional: Evidence Assembly (downstream) depends on Valuation Methodology's implementation (upstream); Valuation Methodology's service and repository logic depends on nothing in Evidence Assembly, and there is no import cycle in either direction.

One narrow, unavoidable exception exists at the *data-type* level, not the service or business-logic level, and this ADR states it rather than leaving it for a reviewer to discover: `MethodologyEvidenceInputContract`'s dataclass is defined in `hunter.evidence_assembly.models` because ADR 0025's already-accepted, unmodifiable `service.py` fixes the Protocol's return type to that exact class (`strict_known_contract(...) -> MethodologyEvidenceInputContract | None`). For `CanonicalValuationMethodologyAuthority.strict_known_contract` to construct and return a value of that exact type (required for `mypy`-clean typing and for `hunter.evidence_assembly.service`'s field-by-field access to work at all), `hunter.valuation_methodology.service` must import that one dataclass from `hunter.evidence_assembly.models`. This is a leaf, dependency-free data-type import — `hunter.evidence_assembly.models` itself imports only `hunter.value_capture.models` and carries no business logic, no service reference, and no import of `hunter.valuation_methodology` or `hunter.evidence_assembly.service` — so it introduces no cycle and no coupling to Evidence Assembly's actual authority, construction, or validation logic. It is the one, bounded, unmodifiable-code-forced deviation from an otherwise strictly one-directional dependency graph; every other aspect of ownership belongs exclusively to `hunter.valuation_methodology`, exactly as this section's opening paragraph states.

### Evidence Shape Registry Authority

Unchanged from revision 1: owned by `hunter.evidence_assembly`, new repository, no correction lineage (immutable per version, new content is a new version), amendment governed by the ADR 0023 pattern. See "Canonical envelope" below for the complete, Finding-4-conformant specification (revision 1 specified this narratively; revision 2 restates it against the explicit envelope template every record family must now use).

### Evidence Semantics Authority

**Resolved canonical classification-authoring authority and deterministic rule source.** Hunter establishes a new governed, versioned reference-data artifact, `EvidenceSemanticsClassificationRuleset`, structurally and governance-wise identical to `EvidenceShapeRegistry` (same package, same amendment discipline, same "no correction lineage — new content is a new version" rule, same ADR-governed-amendment-only content changes per the ADR 0023 pattern). Each ruleset version is a deterministic, total function from a native `FundamentalEvidenceRecord`'s own fields (`evidence_type`, `source_methodology`, `attribution_rule_id`, `unit`) to the six classification outputs `AuthoritativeEvidenceSemantics` must carry (`shape_id`, `currency`, `raw_unit`, `accounting_meaning`, `supply_basis_id`, `pathway_id`), or to an explicit "no matching rule" outcome for inputs it does not cover.

**Resolved service owner:** a new service, `CanonicalEvidenceSemanticsAuthority`, in `hunter.evidence_assembly` — a distinct class from `CanonicalEvidenceAssemblyService`, preserving the already-accepted constructor-injection boundary (`evidence_semantics_authority` is injected into `CanonicalEvidenceAssemblyService`, so it cannot be the same object). It owns applying the in-force `EvidenceSemanticsClassificationRuleset` to a native evidence record and persisting the resulting `AuthoritativeEvidenceSemantics`.

**Resolved persistence owner:** a new repository, `EvidenceSemanticsRepository`, in `hunter.evidence_assembly`.

**Resolved rule versioning:** `EvidenceSemanticsClassificationRuleset` carries an explicit, persisted `acceptance_sequence: int` field — a monotonically increasing integer assigned at the moment each version's governing ADR amendment is accepted (1 for the first published version, 2 for the second, and so on) — as its total-ordering key, never lexicographic string comparison on `version`. This closes, with a concrete field rather than an inferred rule, the "v9"/"v10" ordering ambiguity a naive string comparison would introduce, and the ADR-acceptance-order ambiguity a purely date-derived ordering could introduce for two versions accepted by amendments to the same ADR. Full specification: see "Canonical envelope" below.

**Resolved authorship: who may publish a classification.** Only `CanonicalEvidenceSemanticsAuthority`, and only as the deterministic output of applying one exact, named `EvidenceSemanticsClassificationRuleset` version to one exact, named `FundamentalEvidenceRecord` version. There is no API, method, or path by which a caller supplies a classification's output fields directly.

**Resolved manual exceptions: prohibited, explicitly.** No per-record human override, manual classification, or ad hoc exception path exists at any authority in this chain. A `FundamentalEvidenceRecord` no strict-known `EvidenceSemanticsClassificationRuleset` version can classify remains explicitly unavailable (`strict_known_semantics` returns `None`), never manually asserted. This is required by ADR 0025's own already-accepted rejection of "ad hoc human manifest approval... without persisted authority" (§"Alternatives Considered") applied one layer upstream of assembled evidence itself, and by Constitutional Rule 6 (Explainability), which prohibits an authority whose output cannot be traced to a governed, reproducible rule.

**Resolved conflict behavior:** because classification is a pure, deterministic function of `(evidence_record_id, evidence_record_version, ruleset_version)`, two classification attempts under the *same* ruleset version can never disagree by construction; there is no "competing classification" conflict class analogous to `AssemblyConflictRecord`'s omitted-evidence conflicts. The only conflict this authority recognizes is two independent root records (no `supersedes_record_id` on either) sharing the same logical identity (see "Canonical envelope" below) with different content — an implementation-error case, not a business conflict, surfaced and rejected exactly as `_authorize_correction`'s existing "a root record already exists" pattern already does elsewhere in this repository (`hunter.evidence_assembly.service`, `hunter.valuation.service`, `hunter.valuation_methodology.service`).

**Resolved missingness behavior:** unchanged from `assemble()`'s existing code — a `None` return from `strict_known_semantics` is already treated as `CanonicalEvidenceAssemblyError("no exact strict-known authoritative evidence semantics")` (`service.py:280-281`). No new missingness behavior is introduced.

**Resolved strict-known selection algorithm:** see "Canonical envelope" below.

## Canonical envelope (resolves Finding 4, all four record families)

Every field below is either present on the existing, unmodified dataclass (`MethodologyEvidenceInputContract`, `AuthoritativeEvidenceSemantics` in `src/hunter/evidence_assembly/models.py`; `ValuationMethodologySnapshot` in `src/hunter/valuation_methodology/models.py`) or is a new field this ADR authorizes adding, for each of the four record families this ADR governs: `MethodologyEvidenceInputContract`, `EvidenceShapeRegistry` (unchanged from revision 1), `AuthoritativeEvidenceSemantics`, and the new `EvidenceSemanticsClassificationRuleset`. No field or algorithm is left for a future implementation issue to invent.

### `MethodologyEvidenceInputContract`

**One identity model, no competing identifiers (resolves round-2 Finding 2).** `MethodologyEvidenceInputContract` already has two fields, `contract_id: str` and `contract_version: str` (`src/hunter/evidence_assembly/models.py:100-101`), and these are the *exact* parameter names `MethodologyContractAuthority.strict_known_contract(*, contract_id, contract_version, known_by)`'s already-fixed protocol signature (`service.py:41-44`) queries by. This ADR does **not** add a separate `record_id` or `logical_id` field to this dataclass — doing so would create exactly the "multiple competing identities" this finding correctly rejects. Instead:

- **`contract_id`** (existing field) is the **persisted, queried, immutable logical identity**: a deterministic hash of `(governing_methodology_logical_id, entity_id, representation_id, value_capture_pathway_id, currency, unit, accounting_window_start, accounting_window_end)`. It is stable across corrections to the same target's declaration and changes only if the target scope itself changes (which is a new declaration under a new `contract_id`, not a correction).
- **`contract_version`** (existing field) is the **persisted, queried replay coordinate that changes per correction** — a free-form semantic-version string (e.g., `"1.0.0"`, `"1.0.1"`), following the identical caller-supplied convention every other record family in this repository already uses for its own semantic-version field (e.g., `AssembledFundamentalEvidenceRecord.semantic_version`), just carried under this dataclass's own pre-existing field name rather than a newly invented one.
- `content_hash` (existing field) is the content-addressing identity used to detect and reject a divergent duplicate at the same `(contract_id, contract_version)` — filling the role a separate `record_id` would otherwise play, exactly as `EvidenceShapeRegistry`'s existing `content_hash` field already does for that record family without a `record_id` of its own.

**`value_capture_pathway_id` is a mandatory dataclass field, not only a hash-formula input (resolves round-3 Finding 2).** Revision 3 named `value_capture_pathway_id` as one of the seven inputs to `contract_id`'s hash (immediately above) and, in "Supporting authority ownership" below, described the contract as scoped to one "entity/representation/pathway/currency/unit/accounting-window combination" — but never added `value_capture_pathway_id` as an actual field on `MethodologyEvidenceInputContract` (`src/hunter/evidence_assembly/models.py:99-125`, re-verified against this revision: no such field exists), leaving the hash formula referencing a value the dataclass had no way to carry. Independent review's third round correctly identified this as present only in prose. `hunter.value_capture` pathway scoping is not optional here: ADR 0025 (Accepted) Assembly precondition 3 already requires "every candidate constituent shares the same value-capture pathway," its "Methodology contract" section already requires the contract to declare "continuity requirements (entity, representation, value-capture pathway boundaries the methodology will and will not tolerate crossing)," and `AssembledFundamentalEvidenceRecord`'s own already-accepted Scope table already carries a "value-capture pathway ID" field (`0025-canonical-valuation-evidence-assembly-authority.md`, "Assembled Fundamental Evidence record family" → "Scope"). Removing pathway scope from the contract would leave the contract unable to state a requirement ADR 0025 already mandates it state; this revision therefore adds the field rather than removing pathway from the identity model:

- **`value_capture_pathway_id: str`** — **new, mandatory field.** Required, non-null, non-blank, validated identically to `entity_id`/`representation_id`/`currency`/`unit` (added to this dataclass's existing blank-rejection check, `models.py:127-137`). Names the exact value-capture pathway (the same `ValueCaptureRuleSnapshot` mechanism/entitlement identity ADR 0025 Assembly precondition 3 and the Scope table above both already reference) this contract's declaration applies to.
- **Identity and uniqueness.** Already included in `contract_id`'s hash tuple (above); this field's addition makes that inclusion real rather than aspirational. Because `contract_id` is the sole logical identity (no separate `logical_id` field), two contracts differing only in `value_capture_pathway_id` necessarily hash to two different `contract_id` values — they are two independent, non-competing per-target declarations (one per pathway), never a conflict, and never resolvable to the same `strict_known_contract` query.
- **Validation against the assembly request's exact pathway.** `_validate_methodology_contract` (`service.py:339-387`) already compares the fetched contract's `entity_id`, `representation_id`, `currency`, and `unit` against the specific assembly target (`first = constituents[0]`) but has no equivalent check for pathway today. This revision requires one additive check, symmetric to the four that already exist: `contract.value_capture_pathway_id != first.pathway_id` must reject with `CanonicalEvidenceAssemblyError("methodology contract pathway mismatch")` — see "Exact, bounded additions to already-accepted `hunter.evidence_assembly` code," below, for the complete, explicit statement of this change; it is not made by this ADR or this PR.
- **Correction and replay behavior.** Identical to every other field already listed as a `contract_id` hash input: a `value_capture_pathway_id` change is, by construction, a *new* declaration under a new `contract_id`, never a correction (`supersedes_contract_version` corrections vary only `contract_version` within one fixed `contract_id`, hence one fixed pathway). Replay of a specific `(contract_id, contract_version)` pair always resolves the same pathway every time, since pathway is baked into `contract_id` itself and `contract_id` never changes across a correction lineage.
- **Conflict behavior for two contracts claiming the same target but different pathways.** Not a conflict, by construction: "the same target coordinates" already includes pathway as one of the seven identity-defining coordinates, so two contracts differing only in pathway are, definitionally, declarations for two *different* targets — each gets its own `contract_id`, each is independently authored, persisted, and queried, and neither can ever collide with, supersede, or be rejected as a divergent duplicate of the other. The only conflict this record family recognizes remains the existing one: two independently-authored records sharing the identical `contract_id` (all seven coordinates, including pathway, equal) with divergent content — rejected at persistence time exactly as already specified below.

| `effective_at`, `recorded_at`, `known_at` (existing) | Standard bitemporal envelope, unchanged semantics from every other record family in this repository. |
| `supersedes_contract_version`, `correction_reason` | **New fields**, single-predecessor correction lineage *within the same `contract_id`*: `supersedes_contract_version: str | None` names the exact prior `contract_version` this record corrects (not a `record_id`, since none exists on this dataclass); `bool(supersedes_contract_version) == bool(correction_reason.strip())`, mirroring `ValuationMethodologySnapshot._validate_correction`'s existing rule (`models.py:147-151`), adapted to this dataclass's actual field names. |
| **Provenance** | `governing_methodology_record_id`, `governing_methodology_logical_id`, `governing_methodology_semantic_version` (new fields; the exact `ValuationMethodologySnapshot` this contract was authorized under — consumed by the Finding-1-resolved retrieval algorithm above); `authorized_by` (new field, mirrors `ValuationMethodologySnapshot.authorized_by`, `models.py:69`). |
| `value_capture_pathway_id` | **New, mandatory field** — see above. Required, non-blank; part of `contract_id`'s identity hash; validated against the assembly request's exact pathway. |
| `quality_state`, `conflict_state` (existing) | Standard, same enums as every other record family. |
| Missingness/availability | Not a field — a behavior: unavailable is represented by `strict_known_contract` returning `None`, never by a stored "unavailable" record. |

**Exact uniqueness constraint**: at most one record may exist per exact `(contract_id, contract_version)` pair with divergent content; a second, content-differing record for the same pair is rejected at persistence time (mirroring `AssembledEvidenceRepository._insert_authorized`'s existing divergent-duplicate rejection, `repository.py:76-112`).

**Strict-known selection algorithm**: `strict_known_contract(contract_id, contract_version, effective_as_of, known_by)` returns the unique record matching the exact `(contract_id, contract_version)` pair — with `contract_id` itself already pathway-scoped, per above — whose `effective_at`, `recorded_at`, `known_at` are all `<= known_by`, whose `quality_state == "accepted"` and `conflict_state in {"none", "resolved"}`, **and** whose governing `ValuationMethodologySnapshot` passes the three-step check specified above under "Resolved conflict/disagreement behavior," evaluated at the identical `(effective_as_of, known_by)` pair — otherwise `None`. Because `contract_version` is an exact match (not "latest"), and divergent duplicates are rejected at persistence time, at most one record can ever satisfy the query: selection is unambiguous by construction, with no tie-breaking rule needed.

**Correction successor vs. unresolved conflict**: a correction successor explicitly names its predecessor via `supersedes_contract_version` with a strictly later `recorded_at`/`known_at` and a mandatory `correction_reason` — a deliberate, authorized act, and one that (per above) can never change `value_capture_pathway_id`, since doing so would change `contract_id` and therefore be a new declaration, not a correction. An unresolved conflict is two records with no such predecessor/successor relationship sharing the same `contract_id` (e.g., two independent roots, necessarily agreeing on pathway since `contract_id` already fixes it) — rejected at persistence time before it can ever reach strict-known selection, so no `conflict_state == "open"` case is reachable for this record family in practice (unlike Evidence Semantics, below, where the "no matching rule" outcome creates a legitimate, non-error missingness case rather than a conflict).

**Strict-known selection algorithm**: `strict_known_semantics(evidence_record_id, evidence_record_version, known_by)` — note this protocol signature, already fixed by `service.py:51-54`, carries no `ruleset_version` parameter — selects, among all `AuthoritativeEvidenceSemantics` records for the given `(evidence_record_id, evidence_record_version)` whose own `effective_at`/`recorded_at`/`known_at` are `<= known_by` and `quality_state == "accepted"`/`conflict_state in {"none","resolved"}`, the one produced under the **highest `ruleset_version`** (by acceptance order, not lexicographic order — see "Resolved rule versioning," above) whose *own* `EvidenceSemanticsClassificationRuleset` record is *itself* independently strict-known at the same `known_by`. **Correction successor vs. unresolved conflict**: a correction successor supersedes an erroneously-computed classification *within the same* `(evidence_record_id, evidence_record_version, ruleset_version)` logical lineage, via `supersedes_record_id` and mandatory `correction_reason` — this fixes a bug in the authority's own application of a still-correct ruleset, never a ruleset content change (which instead produces an independent, parallel logical lineage under a new ruleset version, per "Resolved conflict behavior," above). ### `EvidenceSemanticsClassificationRuleset` (resolves Finding 4)

This record family did not have a complete, standalone specification in revision 2; it was described only narratively, alongside `AuthoritativeEvidenceSemantics`, which independent review correctly identified as incomplete. It is a wholly new record family (unlike `EvidenceShapeRegistry`, which already exists in `src/`) — this ADR is its sole architectural source, and every dimension below is fully resolved, not left to implementation.

- **Canonical record family**: `EvidenceSemanticsClassificationRuleset` — a new, immutable, versioned reference-data record, structurally identical in kind to `EvidenceShapeRegistry` (`src/hunter/evidence_assembly/registry.py:13-53`): a `version`-identified snapshot containing a set of deterministic classification rules, each an exact-match tuple `(evidence_type, source_methodology, attribution_rule_id, unit) -> (shape_id, currency, raw_unit, accounting_meaning, supply_basis_id, pathway_id)`, or an explicit absence for inputs the version does not cover (a genuine, non-error "no matching rule" outcome, per "Resolved manual exceptions," above).
- **Repository owner**: `EvidenceSemanticsRepository` (already named as the persistence owner for `AuthoritativeEvidenceSemantics`, above) — extended with a second table and mechanical methods for `EvidenceSemanticsClassificationRuleset`, mirroring `AssembledEvidenceRepository`'s already-audited precedent of one repository class owning two related record families (E-013 in ADPR-0005's Evidence Inventory). No new repository class and no new package.
- **Persistence identity**: `version: str` is the sole persisted identity, mirroring `EvidenceShapeRegistry`'s existing pattern and ADR 0023's `SUPPLY_COHERENCE_RELATIVE_TOLERANCE` precedent.
- **Logical identity**: not applicable, for the identical reason `EvidenceShapeRegistry` has none — a ruleset version is immutable reference data; `version` alone is the identity.
- **Immutable envelope**: `version: str`, `acceptance_sequence: int` (new — see "Version ordering," below), `rules: tuple[...]` (the deterministic mapping entries), `effective_at: datetime`, `recorded_at: datetime`, `known_at: datetime`, `quality_state: Literal["accepted"]`, `conflict_state: Literal["none", "resolved"]`, `content_hash: str`. No `supersedes_*`/`correction_reason` fields — a Registry-family version is amended by publishing a new version, never corrected in place, identical to `EvidenceShapeRegistry`'s already-resolved rule.
- **Strict-known replay**: a new method on `CanonicalEvidenceSemanticsAuthority`, `strict_known_ruleset(*, version: str, known_by: datetime) -> EvidenceSemanticsClassificationRuleset | None` — an exact-match lookup on `version`, filtered to `effective_at`/`recorded_at`/`known_at <= known_by` and `quality_state == "accepted"`/`conflict_state in {"none", "resolved"}`. This method is entirely new (not constrained by any pre-existing Protocol, unlike the three original ADR 0025 collaborators), so it is free to take exactly this signature.
- **Version ordering / acceptance ordering**: `acceptance_sequence: int` is assigned once, permanently, when a version is accepted (the Nth `EvidenceSemanticsClassificationRuleset` version ever accepted, across this record family's entire history) — never reassigned, never inferred from `version`'s string form or from ADR numbering. Total ordering is strictly `acceptance_sequence` ascending; no two versions may ever share a value.
- **Deterministic selection algorithm**: for a given `known_by`, the *set* of strict-known ruleset versions is every version whose `effective_at`/`recorded_at`/`known_at <= known_by` and `quality_state`/`conflict_state` are accepted/non-conflicted; the *selected* version is the one with the maximum `acceptance_sequence` among that set — unique and unambiguous by construction, since `acceptance_sequence` values are unique integers with no ties possible. This is the exact algorithm `AuthoritativeEvidenceSemantics.strict_known_semantics` (above) already invokes as "the highest `ruleset_version` ... by acceptance order."
- **Correction lineage**: not applicable, identical reasoning to `EvidenceShapeRegistry` — content changes are new versions, never corrections.
- **Repository retrieval API**: `EvidenceSemanticsRepository.get_ruleset(version: str) -> EvidenceSemanticsClassificationRuleset | None` (mechanical, exact-match by version) and `EvidenceSemanticsRepository.ruleset_versions() -> tuple[EvidenceSemanticsClassificationRuleset, ...]` (mechanical, full history) — the repository performs no strict-known filtering or selection itself (ADR 0009); `CanonicalEvidenceSemanticsAuthority.strict_known_ruleset` applies the deterministic selection algorithm above over `ruleset_versions()`'s result, exactly mirroring how `CanonicalValuationMethodologyAuthority._strict_known` already applies selection logic over `ValuationMethodologyRepository.records()`'s mechanical output (`service.py:214-231`).

| `ruleset_version` | The exact `EvidenceSemanticsClassificationRuleset.version` the classification was produced under — this record family's sole identity (§"Canonical envelope" → `EvidenceSemanticsClassificationRuleset`, above); satisfies this field's "ruleset ID or canonical ruleset identity" requirement directly, since no separate `ruleset_id`/`logical_id` exists for this record family, for the identical reason already established for `EvidenceShapeRegistry`. | `semantics.ruleset_version`, cross-verified equal to `ruleset.version` (the newly-fetched ruleset, item 3 of "Exact, bounded additions," above). |
| `ruleset_content_hash` | The exact `EvidenceSemanticsClassificationRuleset.content_hash` consulted. | `ruleset.content_hash`. |
| `ruleset_acceptance_sequence` | The ruleset's own `acceptance_sequence: int` (§"Canonical envelope" → `EvidenceSemanticsClassificationRuleset`, above). Not an identity field — `ruleset_version` alone is sufficient identity — carried for audit/debugging traceability only, so a reviewer can see the ruleset's total-ordering position without a separate lookup. | `ruleset.acceptance_sequence`. |
| `semantics_effective_at` | The exact `AuthoritativeEvidenceSemantics.effective_at` consulted — the semantic classification's own effective time. | `semantics.effective_at`. |
| `semantics_known_at` | The exact `AuthoritativeEvidenceSemantics.known_at` consulted — the replay coordinate proving the classification was itself knowable at assembly time. | `semantics.known_at`. |

**Deterministic ordering and hashing.** `constituent_semantic_lineage` is ordered identically, index-for-index, to `constituent_record_ids`/`constituent_shape_ids`/every other per-constituent Lineage field, under the same `deterministic_constituent_order` rule ("accounting_period_start-then-record_id") that already governs them; a lineage tuple of any other length or order is a construction error (§"Exact, bounded additions," item 5, above). Every field of every entry participates in the assembled record's deterministic content identity: each constituent's dictionary inside `assemble()`'s existing `content_basis["constituents"]` list (`service.py:193-202`) gains this entry's fields, so `assembly_content_hash` is sensitive to the exact semantics/ruleset identities consulted; and because `constituent_semantic_lineage` becomes an ordinary dataclass field of `AssembledFundamentalEvidenceRecord`, it is automatically included in `asdict(record)` and therefore in the record's own `content_hash` (`service.py:266`) without any separate hashing mechanism.

**Replay behavior.**

1. Historical replay of an already-persisted `AssembledFundamentalEvidenceRecord` uses exactly the persisted `constituent_semantic_lineage` entries. It never re-invokes `evidence_semantics_authority.strict_known_semantics`/`strict_known_ruleset` to recompute "what the classification would be now" — that would be re-derivation, not replay, and is exactly the "current/latest fallback" ADR 0020 and ADR 0025's "Temporal and replay semantics" item 7 already prohibit.
2. It must never reinterpret an old assembly using a newer ruleset: because the lineage entry is a durable field of an immutable record (ADR 0025's Temporal and replay semantics item 8, unaffected by this amendment), no read path can substitute a later ruleset's classification for what an existing record already, permanently, states it used.
3. Any code that audits or reconstructs a historical assembled record's semantic basis performs the identical *kind* of check round-3 Finding 1's resolution (above) establishes for the governing methodology snapshot: direct exact-record retrieval of the cited `semantics_record_id` and `ruleset_version` (a `get`-by-identity lookup, not a `strict_known_*` selection), confirming both still exist with the cited `content_hash`, and confirming `semantics_effective_at`/`semantics_known_at` (and the ruleset's own bitemporal fields) are each `<=` the assembled record's own `known_at`. It never re-runs `strict_known_semantics`/`strict_known_ruleset`'s current-cutoff selection algorithm against a freshly reconstructed "as of now" cutoff.
4. Unavailable, conflicting, or unresolvable semantic lineage — a cited `semantics_record_id` or `ruleset_version` that no longer resolves, or whose retrieved `content_hash` disagrees with the persisted entry — fails closed: an explicit error, never a substituted, best-effort, or silently-skipped reconstruction.

**Correction behavior.** A correction to a constituent's classification (a new `AuthoritativeEvidenceSemantics` correction, or a new `EvidenceSemanticsClassificationRuleset` version) never mutates any existing `AssembledFundamentalEvidenceRecord`'s `constituent_semantic_lineage`. It can only make a new, successor assembly eligible once every assembly precondition is again satisfied, via the already-accepted `supersedes_record_id`/`correction_reason` mechanism (ADR 0025 Temporal and replay semantics item 8) — the successor persists its own, freshly-resolved `constituent_semantic_lineage`, referencing the corrected classification or new ruleset version; the predecessor's lineage remains exactly as originally persisted, permanently. This is the identical append-only correction discipline ADR 0025 already establishes for constituent corrections generally, applied explicitly to the one new field this amendment adds.

**Hash behavior.** Covered above under "Deterministic ordering and hashing": exact semantic-record and ruleset identities and content hashes participate in both `assembly_content_hash` and the record's own `content_hash`, so any divergence in the semantic basis a replay reconstructs — even one that leaves every native constituent field identical — changes the record's identity rather than silently passing as an equivalent replay.

No other part of ADR 0025 — including its lossless-only rule, assembly preconditions, every "Temporal and replay semantics" item's own text (items 1-12, all unmodified; items 6-8 in particular are relied upon and extended in application to the new `constituent_semantic_lineage` field by this amendment's "Replay behavior" and "Correction behavior" subsections above, without any change to their own wording), conflict-resolution rules, or compatibility table — is changed by this ADR.

## Consequences

Positive:

- Every material design question independent review raised is resolved by a single, named, unambiguous decision — no alternative is left open for implementation to choose.
- The activation/declaration split (snapshot field + per-target sibling record) satisfies ADR 0025's literal accepted text exactly, closing the normative-contradiction risk revision 1 left open as OQ-004.
- Methodology Contract ownership is fully coherent under `hunter.valuation_methodology`: one service, one repository, no split ownership, and no service-level or business-logic dependency on `hunter.evidence_assembly` from the upstream owner — only one narrow, unavoidable data-type import (see "Package ownership and dependency direction").
- Evidence Semantics gains a fully specified, deterministic, auditable authoring model with manual exceptions explicitly and permanently prohibited — closing the Constitutional Rule 6 (Explainability) risk revision 1 left open as OQ-002.
- Every one of the three record families now has a complete canonical envelope, uniqueness constraint, strict-known selection algorithm, and correction-vs-conflict distinction — no implementation issue can silently invent architecture to fill a gap.
- The governing-snapshot eligibility check is now evaluated at the assembly's own decision coordinates rather than the referenced snapshot's own `effective_at`, so a later-effective successor that withdraws assembled-evidence acceptance is actually detected, closing a fail-*open* gap round 3 correctly identified.
- `value_capture_pathway_id` is now an actual, mandatory, hashed, validated field rather than a value only the hash formula's prose referenced, closing the gap between what the identity model claimed and what the dataclass could actually carry.
- `AssembledFundamentalEvidenceRecord` can now durably answer "exactly which evidence-semantics classification and ruleset version validated this constituent," closing a real replay-exactness gap between what `_validate_authoritative_semantics` already resolves at assembly time and what the record persists.

Costs and risks:

- Three authorities (Methodology Contract's two collaborating records, Evidence Shape Registry, Evidence Semantics' two collaborating records) must still be implemented, tested, and independently reviewed before Issue #190 can be unblocked — this ADR authorizes architecture, not implementation effort.
- `EvidenceSemanticsClassificationRuleset`'s initial rule content (which `evidence_type`/`source_methodology`/`attribution_rule_id` combinations map to which `shape_id`/`accounting_meaning`) is not authored by this ADR; a future ADR amendment must publish the first version before any real evidence record can ever be classified. This ADR authorizes the mechanism, not the first version's content — publishing governed reference-data content is itself a future ADR-governed act, consistent with how ADR 0025 itself authorized the Evidence Shape Registry's mechanism without publishing its first version's content.
- Adding `accepts_assembled_evidence` to `ValuationMethodologySnapshot`; `schema_version`, `supersedes_contract_version`, `correction_reason`, `value_capture_pathway_id`, and the `governing_methodology_*`/`authorized_by` provenance fields to `MethodologyEvidenceInputContract`; and `logical_id`/`supersedes_record_id`/`correction_reason`/`ruleset_version` to `AuthoritativeEvidenceSemantics` is additive but requires updating every existing construction site in `tests/test_canonical_evidence_assembly.py` and `hunter.valuation_methodology`'s own test fixtures — a concrete, bounded implementation cost, not a blocking architectural defect.
- **New in this revision.** Five narrowly bounded, explicitly enumerated signature/call-site additions to already-accepted, currently production-unreachable code are now required (see "Exact, bounded additions to already-accepted `hunter.evidence_assembly` code," above): an `effective_as_of` parameter on `MethodologyContractAuthority.strict_known_contract`; one new pathway-equality check in `_validate_methodology_contract`; a `strict_known_ruleset` method on the `EvidenceSemanticsAuthority` Protocol; a return-value change to `_validate_authoritative_semantics`; and nested-datetime (de)serialization in `AssembledEvidenceRepository`. None changes existing validation behavior for any currently-reachable caller (none exists), but all five are real, bounded implementation cost a future issue must budget for, not costless documentation.
- **New in this revision.** `AssembledFundamentalEvidenceRecord` gains one new required field, `constituent_semantic_lineage`, and its embedded `SemanticLineageEntry` structure — a genuine, acknowledged change to ADR 0025's canonical record family (see "Exact amendment to ADR 0025's 'Assembled Fundamental Evidence record family' → 'Lineage' table," above), not a change this revision claims is absorbed into "unchanged" record-family text elsewhere.

## Alternatives Considered

### Fold the full per-target contract directly onto `ValuationMethodologySnapshot` (conform to ADR 0025's literal text with no sibling record at all)

Rejected. `_validate_methodology_contract`'s existing, unmodifiable code requires the fetched contract to carry one exact target's `entity_id`/`representation_id`/`accounting_window`; folding these onto `ValuationMethodologySnapshot` would make "the methodology" itself entity-specific, forcing a new methodology-snapshot "correction" for every new target — corrupting correction lineage, which is meant to represent methodology refinement, not target enrollment. The resolved hybrid (activation field + per-target sibling) satisfies the same accepted text without this defect.

### Standalone sibling record with no reference to `ValuationMethodologySnapshot` at all (revision 1's design)

Rejected on independent review and superseded by this revision. Left ADR 0025's "the `ValuationMethodologySnapshot` in force explicitly declares acceptance" text unsatisfied — no snapshot field asserted anything, so nothing was actually "declared" by the snapshot itself.

### New standalone package or new service for Methodology Contract, independent of `hunter.valuation_methodology`

Rejected, for the same reason revision 1 rejected it: methodology-level policy already has one canonical owner; a new package or service would duplicate that ownership, violating Constitutional Rule 5.

### Permit manual exceptions for Evidence Semantics classification, with a documented approval/provenance process

Rejected. Every exception path this alternative would require — who approves, what provenance an approval carries, how an approval replays — reintroduces exactly the "ad hoc human manifest approval... without persisted authority" failure mode ADR 0025 already rejected for composed *values*, one layer upstream, for classification *inputs* to those same values. A governed, versioned, deterministic ruleset achieves the same coverage-over-time (new evidence shapes get covered by publishing a new ruleset version, exactly as new Evidence Shapes are added to the Registry) without ever needing a per-record exception.

### Derive Evidence Semantics classification from a single global "current" ruleset, not per-classification-record ruleset versioning

Rejected. Would violate ADR 0020's strict-known replay requirement directly: a later ruleset correction would silently reclassify every historical evidence record on next read, exactly the failure mode ADR 0023's own precedent (and its explicit warning about un-versioned constants) already identifies and prohibits.

### Re-derive each constituent's semantic classification at replay time instead of persisting `constituent_semantic_lineage` (new in this revision)

Rejected. Re-running `strict_known_semantics`/`strict_known_ruleset` against a reconstructed "as of now" or "as of the requested cutoff" query at replay time is not equivalent to consulting what the original assembly actually used: a new, more-refined-yet-still-knowable ruleset version published between the original assembly and the replay attempt could cause the re-derived selection to differ from the original one, silently changing what an already-persisted `AssembledFundamentalEvidenceRecord` is understood to rest on — the identical "current/latest fallback" and "later correction silently reclassifies a historical record" failure modes ADR 0020, ADR 0025's Temporal and replay semantics item 7, and the immediately preceding alternative all already reject, one layer downstream. Persisting the exact lineage the original assembly consulted, and requiring replay to consult that persisted lineage directly rather than re-select it, is the only design consistent with ADR 0025's own already-accepted exact-reconstruction requirement (Temporal and replay semantics item 6).

### Add only `ruleset_version` to `constituent_semantic_lineage`, omitting the semantics-record-level fields

Rejected. `ruleset_version` alone would prove which ruleset *could* classify the constituent but not which specific `AuthoritativeEvidenceSemantics` record — including its own correction lineage, since a ruleset version can be reapplied by a corrected `CanonicalEvidenceSemanticsAuthority` run — was actually consulted at assembly time. Omitting `semantics_record_id`/`semantics_logical_id`/`semantics_semantic_version`/`semantics_content_hash` would leave a hostile reviewer able to reproduce round-3 Finding 3's original "insufficient for exact historical replay" complaint one field narrower; the full entry defined above is the minimum that actually satisfies "reconstruct the exact original decision."
